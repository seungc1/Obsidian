# 폐점 리스크 모델 — 웹사이트 시연 시나리오 (비교 매장 기반)

[[1. Projects/폐점 재계약 리스크 조기경보 모델]]의 로컬 웹사이트(`web/dashboard.html`·`store-list.html`·`prospect-district.html`·`store-detail.html`, [[3. Resources/폐점 리스크 모델 - 코드 파일 구성]] 참고)가 실제로 어떤 가치를 내는지 보여주기 위한 시연 시나리오 모음. 가상 인물이나 지어낸 숫자 없이, **216개 실매장 데이터(`data/interim/kimgane_risk_rankings.json`)에서 실제로 뽑은 "비교가 성립하는" 매장 쌍**만 골랐다 — 두 매장이 여러 조건은 비슷한데 결과(위험도/우선순위)가 다른 경우라야 "이 사이트가 뭘 잡아내는지"가 명확히 보인다.

## 요약 (핵심 3줄)
1. 서울 87개 매장 중 **같은 구 안에서도 위험도가 90점 이상 벌어지는 경우가 흔함**(예: 서초구 7개 매장이 백분위 2.1~93.5로 갈림) — "구 단위로만 봐서는 안 된다"는 이 사이트의 핵심 메시지를 실제 데이터로 증명 가능
2. 위험도(v2 백분위)와 계약 마감 시점(D-day)은 서로 다른 축이라, **위험도만 높다고 최우선이 되는 게 아니다** — 재계약 대상 점검 페이지의 우선순위 로직이 실제로 이 둘을 다르게 다루는 걸 실제 매장 쌍으로 보여줄 수 있음
3. 원자료(유동인구·경쟁밀도 등)를 사람이 직접 눈으로 봐서는 어느 쪽이 더 위험한지 판단하기 어려운 경우가 실제로 존재함(경쟁점포가 적은 매장이 오히려 고위험) — SHAP 근거·서울 평균 비교 기능이 왜 필요한지 스스로 증명

## 시나리오 1 — "같은 구인데 왜 이렇게 다르지?" (전체 매장 목록 → 매장 상세)

**보여주는 기능**: 전체 매장 목록 검색/정렬, 매장 상세의 상권 원자료+서울 평균 비교, 위험도 요약 해석 문장

**대상 매장** (둘 다 서초구, 실제 216개 CSV에 있는 진짜 주소):

|                        | 서울특별시 서초구 잠원로12길 4             | 서울특별시 서초구 방배로 28      |
| ---------------------- | ------------------------------ | --------------------- |
| 입지 위험도(백분위)            | **93.5** (위험한 편)               | **2.1** (서울 전체 최고 안전) |
| 종합 판정                  | 입지 위험 — 업종은 괜찮으나 이 매장 입지가 나쁨   | 안전 — 업종·입지 둘 다 양호     |
| 유동인구(전체)               | 325,836명 (서울 평균 957,297명의 34%) | 53,517명 (평균의 6%)      |
| 경쟁점포(반경 500m)          | 7개 (평균 23개보다 적음)               | 2개 (더 적음)             |
| 폐업 매장 평균영업개월(서울 평균 대비) | **+15.0개월**                    | -3.0개월                |
| 상권변화등급                 | 상권확장 (LH)                      | 다이나믹 (LL)             |
| 최인접 지하철역               | 잠원역 580m                       | 방배역 510m              |

**진행 순서**:
1. "전체 매장 목록"에서 검색창에 "서초구" 입력 → 7개 매장이 뜨는데 위험도가 2.1~93.5로 극단적으로 갈리는 걸 먼저 눈으로 확인시킴("같은 구인데 왜 이렇게 다르죠?"라는 질문을 유도)
2. 위험도가 가장 높은 잠원로12길 4를 클릭 → 매장 상세로 이동, 위험도 요약이 "상위 6.5%로 위험한 편"이라고 문장으로 해석해주는 것 확인
3. "상권 원자료" 섹션에서 헤드라인 숫자(유동인구·배후인구·경쟁점포)가 전부 **서울 평균보다 낮은데도** 위험도가 높다는 역설을 짚음
4. 뒤로 가서 방배로 28(가장 안전한 매장)을 열어 같은 항목을 비교 — 두 매장 다 "한산한 상권"인데 결과가 반대인 이유는 상권변화등급(LH vs LL)과 "폐업 매장 평균영업개월" 같은 다른 신호가 갈리기 때문임을 보여줌
5. "가장 큰 영향 요인" 카드로 마무리 — 잠원로12길은 매출 데이터 결측이 1순위로 잡힘(모델이 "모른다"는 것도 근거로 취급한다는 정직한 사례), 방배로 28은 지하철 접근성(510m)이 1순위

**발표 포인트**: 3번 단계가 임팩트 포인트 — "숫자만 보면 두 매장이 비슷해 보이는데 결과는 정반대"라는 게 바로 이 모델이 필요한 이유(단순 규칙이 아니라 여러 신호를 종합 판단)라는 메시지로 이어감.

## 시나리오 2 — "경쟁점포가 적은데 왜 위험하지?" (U자형 패턴 재확인)

**보여주는 기능**: 위험도가 직관과 반대로 갈 수 있다는 것 → 사이트가 굳이 필요한 이유

**대상 매장**:

|               | 서울특별시 동작구 만양로 6        | 서울특별시 서대문구 이화여대7길 30 |
| ------------- | ---------------------- | -------------------- |
| 입지 위험도(백분위)   | **97.8** (서울 전체 최고 위험) | **0.6** (서울 최상위권 안전) |
| 경쟁점포(반경 500m) | 20개                    | **45개**(더 많음에도 안전)   |

**진행 순서**: "경쟁점포가 많으면 위험할 것 같은데, 실제로는 정반대인 두 매장이 있습니다"로 시작 → 두 매장 상세를 나란히 열어 경쟁점포 수만 보면 예상이 뒤집힌다는 걸 보여줌. [[3. Resources/폐점 리스크 모델 - 피자스쿨 케이스 스터디]]에서 이미 확인된 "U자형 패턴"(너무 한산해도, 너무 붐벼도 위험)이 실제 서울 매장 데이터에서도 재현됨을 짚는 용도 — 신규 발견이 아니라 기존 케이스 스터디 결론의 재확인.

## 시나리오 3 — "위험한데 급한 건 따로 있다" (재계약 대상 점검 우선순위)

**보여주는 기능**: 재계약 대상 점검 페이지의 위험도+긴급도 결합 우선순위 로직

**대상 매장**(공교롭게도 둘 다 노원구, 둘 다 고위험이지만 계약 만료 시점은 정반대 — 계약일자는 216개 CSV에 없어 매장 주소 시드 더미값, [[3. Resources/폐점 리스크 모델 - 더미데이터 현황]] 참고):

| | 서울특별시 노원구 광운로 20 | 서울특별시 노원구 노원로34길 108 |
|---|---|---|
| 입지 위험도(백분위) | 97.2 | 96.2 (둘 다 서울 최상위권 위험) |
| 계약 만료까지 D-day | **D-4**(마감 임박·경과) | D+186(조율 가능 구간) |
| 재계약 대상 점검에서 뜨는 그룹 | "조건변경 통지 마감 임박·경과 + 고위험 동시 해당"(최상단) | "재계약 조율 가능 + 고위험 동시 해당" |

**진행 순서**: "위험도만 보면 두 매장이 거의 똑같이 위험합니다(97.2 vs 96.2) — 그런데 이 사이트는 이 둘을 완전히 다른 우선순위로 놓습니다"로 시작 → 재계약 대상 점검 페이지를 열어 광운로 20이 맨 위(마감 임박) 그룹에, 노원로34길 108이 그 아래(조율 가능) 그룹에 있는 걸 보여줌. 가맹사업법 제13조상 통지 마감(90일 전)을 넘기면 담당자가 손쓸 방법이 없어진다는 배경 설명과 연결.

**발표 포인트**: "위험도 순으로만 정렬했으면 이 둘의 순서가 안 바뀌었을 것"이라는 대조가 핵심 — 이 페이지가 단순 랭킹이 아니라 "지금 뭐부터 해야 하나"에 답하도록 설계됐다는 걸 증명.

## 시나리오 4 — "AI가 후보지를 걸러주고 등급까지 매긴다" (희망상권 탐색)

**보여주는 기능**: 영업지역 게이트(하드 블록) + 상권 적합도 등급, 실제 서초구 격자 후보지 결과

**서초구 격자 후보지 4곳** (이미 계산·캐시된 실제 결과):

| 후보지 | 상권 유형 | 게이트 | 적합도 |
|---|---|---|---|
| 한전아트센터 | 골목상권 | 통과 | 조건부 적합(경쟁밀도 양호, 유동인구·배후인구는 보통) |
| 양재역 | 발달상권 | 통과 | 재검토 권고(유동인구는 매우 높으나 배후인구 백분위 2 — 거주자 기반이 거의 없음) |
| 은광여고 | 골목상권 | 통과 | 재검토 권고(유동인구 백분위 9로 너무 한산) |
| **양재시장** | 전통시장 | **차단** | 반경 500m 내 기존 김가네 매장 1건 존재 — 가맹사업법 §5-2 영업지역 침해로 자동 차단 |

**진행 순서**: "희망상권 탐색"에서 서초구 클릭 → 격자 4곳이 뜨는데 그중 하나(양재시장)는 아예 회색으로 걸러져 있고 사유가 명시돼 있음을 보여줌("사람이 일일이 기존 매장 위치를 대조 안 해도 자동으로 걸러짐") → 통과한 3곳도 등급이 다 다르다는 걸 짚음(양재역은 유동인구는 최고인데 배후인구가 거의 없어 재검토 권고로 밀림 — "겉보기 좋은 자리도 걸러낸다") → 후보지 하나 클릭해 신규가맹 상담자료(예상매출액 산정서 등 법정 서면)까지 그 자리에서 생성되는 것 확인.

**발표 포인트**: 게이트(하드 블록)와 적합도(등급)를 분리해서 설계한 이유 — "기존 가맹점 보호는 협상 여지가 없는 법적 문제, 상권 적합도는 참고용 등급"이라는 구분을 명확히.

## 시나리오 5 — "입지는 안전한데 업종 자체가 흔들린다" (업종 구조적 위험, 더미 1건)

**보여주는 기능**: 전체 매장 목록 → 매장 상세의 "업종 평균 대비" 통계 막대, 2x2 분류 로직(`combine_scores._classify()`)의 세 번째 케이스

**배경**: 216개 실매장 배치 산출물(`data/interim/kimgane_risk_rankings.json`)의 v1_percentile(업종 평균 대비)이 전체 매장 동일하게 11.8로 나오는 문제를 발견(2026-08-11, [[3. Resources/폐점 리스크 모델 - 더미데이터 현황]] 참고) — 그 결과 전체 매장 목록 어디를 봐도 "업종 평균 대비" 항목이 위험으로 뜨는 매장이 하나도 없었음. 근본 원인은 아직 안 고쳤지만, 이 케이스 자체가 실제 분류 로직에 존재하고 시연에 필요해서 매장 1곳만 더미로 덮어씀.

**대상 매장**: 서울특별시 중구 세종대로 28

| | 실제 값 | 더미 오버라이드 |
|---|---|---|
| 업종 평균 대비(v1 백분위) | 11.8 | **82.4** |
| 입지(v2 백분위, 서울 매장) | 0.3 (그대로 유지) | 0.3 |
| 종합 판정 | 안전 — 업종·입지 둘 다 양호 | 업종 구조적 위험 — 입지는 괜찮으나 업종 전체가 흔들림 (업종 트렌드 모니터링) |

**진행 순서**: "전체 매장 목록"에서 세종대로 28을 클릭 → 상세 패널의 "업종 평균 대비" 막대가 빨간색(위험한 편)인데 바로 아래 "입지" 막대는 거의 0에 가까운 걸 대비시킴 → "이 매장은 자리는 좋은데, 김가네라는 업종/브랜드 자체가 전국적으로 흔들리는 신호가 잡혔다"는 케이스로 설명. 시나리오 1(입지만 나쁨)과 정반대 축이라는 걸 짚으면 2x2 분류 매트릭스(업종×입지) 전체를 한 번에 설명 가능.

**발표 포인트**: 이 매장 데이터는 v1 배치 결과가 아직 미완성이라 더미로 만든 것임을 숨기지 말고 밝힐 것 — "업종 축 로직 자체는 실 데이터로 검증됐고(분류 함수는 실제 코드), 지금은 배치 재계산 전이라 예시 하나만 수동으로 넣어뒀다"는 맥락으로 설명하면 됨.

## 참고 — 시연 전 확인할 것
- 모든 수치는 이 문서 작성 시점(오늘) 기준 `data/interim/kimgane_risk_rankings.json`·`data/interim/api_cache/`의 실제 계산 결과다. 배치가 재실행되거나 캐시가 갱신되면 값이 소폭 바뀔 수 있음 — 시연 직전 해당 매장 페이지를 한 번 열어 숫자가 이 문서와 같은지 확인 권장.
- 시나리오 3의 D-day는 더미데이터라 **오늘 날짜 기준으로 계산된 값**이다 — 시간이 지나면 "D-4"였던 광운로 20의 구간이 바뀔 수 있으니, 시연 당일 재계약 대상 점검 페이지에서 직접 확인할 것.
- 서버 포트는 이 세션 동안 여러 번 바뀜(가장 최근은 8050) — [[3. Resources/OhDomi 프로젝트 - 팀 저장소 구성 및 아키텍처]]나 진행 로그에서 최신 포트 확인.
