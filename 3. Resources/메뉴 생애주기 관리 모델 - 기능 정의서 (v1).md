# 메뉴 생애주기 관리 모델 - 기능 정의서 (v1)

> Notion 기능정의서 DB 기준 **FUNC-003-07 메뉴 생애주기 관리**(대분류: 콘텐츠 → 중분류: 매출증대 지원, 우선순위: 확장)의 상세 설계서. 프랜차이즈 통합관리 플랫폼(대기만성홀딩스) 전체 기능정의서 안의 한 기능.

## 0. 오픈 이슈 해결 (확정)

기획 초안에서 남겨둔 3개 오픈 이슈를 Notion 기능정의서 DB를 직접 조회해 아래와 같이 확정한다.

1. **F-ID/넘버링**: "F7"이라는 번호는 실재하지 않는다. 이 기능은 이미 Notion DB에 **`FUNC-003-07`**로 등록돼 있다(대분류 콘텐츠, 중분류 "매출증대 지원", 우선순위 "확장"). F-02/F-04 구코드 잔재 이슈는 별도 문서(F8 고객불만)에 남은 이전 번호체계 흔적이며 이 기능과는 무관 — 재확인/재넘버링 불필요.
2. **"메뉴 미래 수요 예측"과의 통합 여부**: **통합하지 않고 분리 유지**한다. `FUNC-003-01`(매출/발주량 예측)의 "메뉴별판매량예측"은 **판매이력이 있는 기존 메뉴**의 발주·재고용 **단기 수요예측**이고, 본 기능(FUNC-003-07)은 **판매이력이 없는 신메뉴**의 **출시~단종 전체 생애주기 곡선**을 다룬다. 대상(기존 메뉴 vs 신메뉴)과 시계(단기 발주 vs 장기 생애주기)가 다르므로 하나의 기능으로 합치면 콜드스타트 로직과 실측 기반 로직이 뒤섞여 오히려 불명확해진다. 대신 **인계 지점**을 명시한다: 신메뉴가 출시 후 N주 실측 판매 데이터를 확보하면(§7 KPI의 "출시 후 N주" 시점), 이후 예측은 FUNC-003-07의 zero-shot 추정치 대신 FUNC-003-01의 실측 기반 판매량예측으로 자연스럽게 갈아탄다. 두 기능은 데이터 흐름상 이어지는 파이프라인이지 같은 기능이 아니다.
3. **지역군집(수도권/광역시/기타) 분리**: 목표고객사의 전국 매장 지역 분포가 확정되기 전까지는 **분리하지 않는다.** MVP는 "단일 전국 곡선 + 지역 보정계수" 구조로 시작하고(§4 설계원칙 3), 실제 매장 데이터로 지역 이질성이 크게 확인되는 시점에 지역군집 분리를 재검토한다. 지금 곡선 산출 로직을 지역군집별로 미리 분기시켜두는 건 확정되지 않은 고객사 분포를 가정한 과설계이므로 보류.

## 1. 개요

AI가 계절/이벤트/유사 메뉴 판매 이력을 종합해 신메뉴의 출시 시점부터 단종 시점까지 예상 생애주기 곡선을 산출하고, 각 구간별로 손해를 최소화하는 액션(출시 타이밍, 개선사항, 단종 시점)을 지시하는 기능.

**"리포트는 해법이 아니다" 원칙**: 곡선을 보여주는 데 그치지 않고, 지금 이 메뉴가 성장/정체/쇠퇴 중 어느 상태인지와 그에 따른 다음 행동을 명시한다.

## 2. 배경

신메뉴는 태생적으로 자체 판매 이력이 없는 **콜드스타트 대상**이다. 따라서 외부 프록시 신호 + 유사 메뉴 태그 매칭 + zero-shot LLM 조합이 핵심 전략이며, 이는 임시방편이 아니라 이 문제의 구조적 특성이다 — 스케일이 커져도 신메뉴 시점의 콜드스타트 자체는 사라지지 않고, 다만 자사 실측 데이터 축적으로 유사 메뉴 매칭의 정확도가 올라가는 것(Phase 2)일 뿐이다.

## 3. 사용자 역할

- **본사 메뉴기획 담당자** (주 사용자, 출시/개선/단종 의사결정 권한)
- **가맹점주** (열람만 가능, 직접 결정권 없음 — 실제 구매 고객은 본사)
  - 가맹점주 노출 목적: 본사가 결정한 신메뉴 출시/단종 일정을 사전 인지시켜 재고·인력 준비 시간을 주기 위함. 가맹점주용 화면에는 곡선 원본이 아니라 "언제부터/언제까지, 무엇을 준비하라"는 확정된 액션만 노출(FUNC-002-14 "오늘의 할일" 연계 후보).

## 4. 설계 원칙

1. **상태·임계값 관리**: 출력은 곡선 조회가 아니라 "성장/정체/쇠퇴" 3단계 상태 + 권고 조치. **상태 판정 주체는 규칙 기반 임계값**(예: 검색량 인덱스 N주 이동평균의 기울기·변동률 기준)이며, LLM은 임계값 판정 자체가 아니라 그 임계값에 맞춰 원인 해석과 액션 문구를 생성하는 역할로 한정한다. 판정 로직을 LLM에 맡기면 같은 데이터에 다른 날 다른 상태가 나올 수 있어(비결정성) 신뢰도가 떨어지기 때문 — 이 경계는 §6 아키텍처에서 구현 단계로 다시 명시.
2. **Zero-shot LLM 우선**: 커스텀 학습 모델 대신 범용 LLM의 사전지식(한국 외식 계절성 지식) + 실시간 프록시 신호 조합. 별도 학습 인프라 불필요.
3. **도메인시프트 방어**: 서울/특정지역 기반 신호는 "0차 근사치"로만 사용, 전국에 그대로 일반화하지 않는다. (지역 보정계수 적용은 2026-07-31 Phase 2로 이연 — MVP는 지역 보정 없는 단일 전국 곡선. 지역군집 분리도 §0-3에 따라 Phase 2 이후 재검토로 같은 시점에 묶임)
4. **프록시와 실측 구분**: 검색량은 관심의 프록시지 판매의 프록시가 아니므로, 모든 출력에 신뢰도 라벨("권고안·참고용" 등) 필수.
5. **원가 트리거 분리 추적**: 판매량 기반 생애주기 판단과 별개로, 원재료 원가 급등에 의한 조기 단종 트리거를 병행 산출.
6. **(신규) 검증 없는 추정치는 배포하지 않는다**: zero-shot LLM 추정 곡선은 정답 라벨이 없어 정확도를 사전에 알 수 없다. 따라서 배포 전 반드시 §8 백테스트를 통과한 신뢰도 라벨 기준으로만 "권고" 등급을 부여하고, 백테스트가 안 된 신규 카테고리는 자동으로 "참고용" 등급으로 강등한다.

## 5. 데이터 입력 (확정본, 2026-07-30 실사 반영)

기획 초안의 "4계층" 구분을 실사 결과에 맞춰 **MVP 채택 소스 4개 + Phase 2 이연 2개 + 제외/보류 소스**로 정리. 전체 검증 근거는 [[3. Resources/메뉴 생애주기 관리 모델 - 데이터 소스 점검]] 참고.

| 계층 | 소스 | 특성 |
| --- | --- | --- |
| 계절/절기 | 특일정보(공휴일·절기) API | 캘린더 기반이라 예보 시계와 무관하게 항상 유효. (~~KMA 중기예보~~는 2026-07-31 제외 — 향후 11일치뿐이라 수개월짜리 생애주기 곡선에 실효성 낮고, 계절 신호는 이 소스가 이미 커버) |
| 수요 프록시(전국) | 네이버 검색어트렌드 오픈API | 메뉴 키워드별 검색량 시계열(관심도 프록시). **지역 필터 없음** — 전국 단일 지수로만 사용 |
| 원가 리스크 | KAMIS 농산물유통정보 | 핵심 원재료 도소매가 일단위, BOM 연동(BOM 출처는 §12 미해결) |
| 정성 맥락 | 농식품부 외식업 트렌드조사 / 농진청 소비트렌드 | 연간·월간 리포트를 사람이 요약해 LLM 프롬프트 배경지식으로만 투입(파이프라인 아님) |
| 자사 실측 (Phase 2+) | 전국 매장 실제/더미 판매 데이터 | 유사 메뉴 매칭 고도화, 프록시 신호 검증용 |

**Phase 2 이연(2026-07-31)**: KOSIS 서비스업동향조사(시도 단위)·서울 열린데이터광장 추정매출-상권(서울 한정) — 지역 보정계수용으로 신규 채택했던 2개 소스. §0-3에서 지역군집 분리 자체를 목표고객사 확정 전까지 보류해뒀는데 지역 보정계수만 먼저 연동하는 게 앞뒤가 안 맞고, 서울 추정매출은 목표고객사가 비수도권이면 그대로 죽는 데이터라 지금 붙이면 과설계 — 지역군집 분리 재검토와 같은 시점(Phase 2)으로 묶어서 이연. MVP는 지역 보정 없는 **단일 전국 곡선**으로 산출.

**제외/보류**: BC카드 지역별 자영업자 매출분석(승인 대기, 업종 단위라 채택돼도 보조지표 이상은 아님), 소상공인365 전국매출·Google Trends·aT FIS·서울 외 지자체 상권API(자동화 난이도/실효성 부족으로 제외 또는 목표고객사 확정 시 재조사) — 사유 상세는 데이터 소스 점검 문서 §2.

**(§4 설계원칙 3 재정의, 2026-07-31 갱신)** "지역 보정계수"는 애초 기획처럼 시군구 단위로 정밀하게 만들 수 없다는 게 실사로 확인됐고(전국 어디도 시군구 단위 수요 프록시 없음), 그 대안으로 채택했던 2단계 해상도(서울 상권/시도 KOSIS) 보정 로직 자체도 지역군집 분리 보류 결정과 함께 Phase 2로 이연. MVP 단계에서는 지역 보정계수를 아예 적용하지 않고, 서울/특정지역 기반 신호(네이버트렌드 등)는 "0차 근사치"라는 한계만 신뢰도 라벨에 명시하는 것으로 대체.

**(2026-07-30 해소)** BOM 데이터 출처 미정 이슈는 Notion "필요 데이터 정의" DB 대조로 해소됨 — "메뉴별 표준 레시피(BOM)"가 이미 파트=더미데이터·유형=자체생성("팀 작성 임시 레시피표")으로 정의돼 있었고, 이 문서 작성 시점엔 FUNC-003-07과의 연결(연결기능)만 빠져있어 못 찾았던 것. 연결 완료 — 원가 트리거는 이 더미 레시피표 기준으로 구현 가능.

## 6. 유사 메뉴 매칭 로직 & 아키텍처

```
[신메뉴 정보] → 규칙 기반 태그 매칭(카테고리/조리법/주재료/가격대/계절연관성)
             → 1차 후보군(유사 메뉴 N개)
             → LLM: 후보군의 프록시 신호 + 계절·원가 데이터 종합
             → 예상 생애주기 곡선(출시-피크-쇠퇴-단종 권고 시점) + 확신도 등급 산출
             ↓
[규칙 기반 임계값 엔진] ← 검색량 인덱스 이동평균/기울기
             → 성장/정체/쇠퇴 3단계 상태 판정 (결정론적, LLM 개입 없음)
             ↓
[LLM] → 상태별 원인 해석 + 권고 조치 문구 생성 (판정 자체는 하지 않음)
             ↓
[원가 트리거 엔진] ← KAMIS + BOM (판매량 신호와 완전 독립, 병렬 산출)
             → 조기 단종 경보 (판매량 상태와 무관하게 별도 발동)
```

상태 판정과 문구 생성을 분리하는 이유는 §4-1 참고 — 같은 입력에 재현 가능한 상태가 나와야 "성장/정체/쇠퇴"가 의사결정 기준으로 신뢰받는다.

**유사메뉴 매칭 로직 상세 설계**(태그 체계, 스코어링 공식, 후보군 선정 기준, 메뉴 마스터 데이터 갭)는 별도 문서로 분리: [[3. Resources/메뉴 생애주기 관리 모델 - 유사메뉴 매칭 로직 설계]].

## 7. 출력 / 지시 항목

- 출시 최적 타이밍 권고 (근거: 검색량 인덱스 추이)
- 생애주기 상태 3단계(성장/정체/쇠퇴) + 권고 조치
- 원가발 조기 단종 경보 (판매량과 무관하게 별도 발동)
- 메뉴 개선 제안(가격/재료/포지셔닝) — LLM 생성, **인간 검토 필수(사람 검토 없이 자동 실행 금지)**
- 모든 출력 항목에 신뢰도 라벨 부착: `권고안`(백테스트 통과 카테고리) / `참고용`(백테스트 미검증 또는 니치 카테고리 폴백)

## 8. 검증/백테스트 전략 (신규 — 기존 기획의 공백 보완)

기존 기획에는 "MAPE 등" KPI만 있고 **출시 전에 이 추정 곡선이 믿을 만한지 확인하는 절차**가 없었다. 다음을 배포 전 필수 절차로 추가한다.

- **백테스트 방식**: 이미 생애주기를 마친 과거 메뉴(자사 보유 시) 또는 유사 메뉴 판매 공개 사례에 대해, "출시 시점까지의 정보만" 사용해 곡선을 역산 추정 → 실제 곡선과 비교해 MAPE 산출.
- **카테고리별 신뢰도 등급 부여**: 백테스트 표본이 확보된 메뉴 카테고리만 "권고안" 등급 부여 가능. 표본이 없는 카테고리는 자동으로 "참고용"으로 강등(§4-6과 연결).
- **재검증 주기**: 분기 1회, 신규 실측 데이터 누적 시 카테고리별 신뢰도 등급 재산정.

## 9. 예외 처리

- 검색량 데이터가 없는 니치 메뉴 → 카테고리 상위 태그로 폴백
- 원가 데이터 결측 → 원가 트리거 판단 보류, 판매량 기반 판단만 노출
- 매장 간 지역 이질성이 큰 경우 → 단일 전국 곡선 유지, 지역 보정계수는 적용하지 않음(2026-07-31 Phase 2로 이연, §0-3 지역군집 분리와 같은 시점 재검토)
- 백테스트 미검증 카테고리 → 신뢰도 라벨 자동 "참고용" 강등(§8)

## 10. KPI

- 출시 후 N주 내 목표 매출 도달률
- 단종/개선 권고 채택률
- 원가발 조기경보 사후 정확도
- 예측 곡선 대비 실제 판매 곡선 오차(MAPE 등) — 카테고리별로 분리 집계(전체 평균 하나로만 보면 §8 백테스트 목적과 어긋남)

## 11. 관련 기능 연계

- `FUNC-003-01`(매출/발주량 예측): 신메뉴가 실측 데이터를 확보한 이후의 인계처. §0-2 참고
- `FUNC-003-06`(이벤트/할인 적합도 분석): 생애주기 "정체" 상태의 권고 조치 중 하나(할인/이벤트)가 이 기능과 연동될 수 있음
- `FUNC-004-06`(외부 API 연동관리): 네이버트렌드/BC카드/KAMIS 연동 상태가 여기서 관리됨(KMA는 2026-07-31 제외로 대상에서 빠짐)
- `FUNC-002-14`(오늘의 할일): 가맹점주 대시보드에 노출할 확정 액션(준비 일정) 연계 후보 — §3
