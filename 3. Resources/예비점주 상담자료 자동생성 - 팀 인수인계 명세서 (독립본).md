# 예비점주 상담자료 자동생성 - 팀 인수인계 명세서 (독립본)

다른 팀원에게 구현을 넘기기 위한 문서. 링크를 따라가지 않아도 이 문서 하나로 배경·설계·검증·재사용 대상을 전부 파악할 수 있도록, 관련 문서(원안 v1, 폐점 재계약 리스크 조기경보 모델 프로젝트, 그 최종 리포트)의 내용을 전부 인라인으로 포함한다. 중복 허용.

## 0. 한 줄 요약

가맹개발팀의 상담 업무를 "신규 가맹점주"와 "재계약 가맹점주" 두 트랙으로 나눠 자동화한다. 신규 트랙은 법정 필수서류(예상매출액 산정서·인근가맹점 현황문서)를 계산하는 신규 로직이 필요하고, 재계약 트랙은 이미 완료된 별도 프로젝트(폐점 재계약 리스크 조기경보 모델)의 산출물을 그대로 재사용하는 렌더링 계층이면 된다. 매장 마스터 DB의 일부 필드(전용면적·영업개시일)가 아직 확인되지 않았으나, mock 데이터로 지금 개발을 시작하고 실전에서 함수 하나만 실제 DB 연동으로 교체하는 전략을 이미 코드로 검증해뒀다.

**⚠️ 2026-08-05 정정 — 이름이 비슷한 두 산출물 혼동 주의**: closure-risk-model 저장소의 `prospect_packet.py`에 있는 "상권분석" 섹션(유동인구/추정매출/경쟁밀도 등)은 이 문서가 요구하는 신규 트랙의 법정 서면이 **아니다** — 그건 v2(LightGBM 폐업 확률 모델)의 피처를 그대로 노출한 것이고, 계산 방식이 이 문서 1-4절의 법정 예상매출액 산정서(최인접 5개 매장 평균법)와 전혀 다르다. **이 문서가 요구하는 신규 트랙(영업지역 게이트·법정 예상매출액 산정서·인근가맹점 현황문서·ROI)의 실제 구현은 `src/new_franchisee_packet.py`**(2026-08-05 신설, 7절 체크리스트 참고) — 이름이 비슷한 두 파일을 혼동하지 말 것.

## 1. 배경 — 원안(v1) 전체

가맹개발팀 담당자가 처음 작성한 기능 명세서 원문. 아래 2~6절이 이 원안을 검토·개정한 결과이므로, 먼저 원안 자체를 이해해야 무엇이 왜 바뀌었는지 알 수 있다.

### 1-1. 기능 개요

| 항목 | 내용 |
| --- | --- |
| 기능명 | 예비 점주 상담자료 자동생성 |
| 목적 | 가맹개발팀의 후보 입지 상담 시 법정 필수서류(예상매출액 산정서, 인근가맹점 현황문서)와 상담용 자료를 데이터 기반으로 자동 생성 |
| 관련 법령 | 가맹사업거래의 공정화에 관한 법률 제7조, 제9조, 동법 시행령 제9조 |
| 전제조건 | 가맹점 수 100개 이상 또는 비(非)중소기업 가맹본부 (법정 의무 대상) |

### 1-2. 사용자 및 권한

| 역할        | 권한                              |
| --------- | ------------------------------- |
| 가맹개발팀 담당자 | 후보 입지 입력, 산정서 초안 생성, 슬라이드 생성    |
| 법무/승인권자   | 산정서 검토·승인·서명, 재산정 요청            |
| 예비 점주     | 승인 완료본만 열람 (원본 편집 불가, 별도 뷰어 링크) |

### 1-3. 3-1. 상권 적합도 분석 & 판정

**처리 로직**
1. 후보 입지 주소 입력 → 좌표 변환(지오코딩)
2. 반경 N km 내 동일 브랜드 매장 수 조회 (자기잠식 체크)
3. 상권정보시스템 API로 유동인구·배후세대·업종별 점포 수 조회
4. 기준치 대비 등급 산정

**판정 기준 (예시 — 실제 임계치는 클라이언트 출점 기준 확보 후 확정 필요)**

| 지표                 | 적합      | 주의      | 부적합    |
| ------------------ | ------- | ------- | ------ |
| 반경 500m 동일브랜드 매장 수 | 0개      | 1개      | 2개 이상  |
| 배후세대수 (지역 평균 대비)   | 100% 이상 | 70~100% | 70% 미만 |
| 유동인구 (지역 평균 대비)    | 100% 이상 | 70~100% | 70% 미만 |

3개 지표 중 부적합 1개 이상 → 종합판정 "재검토 권고" 자동 라벨링.

**출력**: 상권 스코어카드 (지표별 값, 등급, 종합판정)

### 1-4. 3-2. 예상매출액 산정서 (법정 서면)

전체 명세서에서 가장 엄격한 기능 — 시행령이 계산 방식을 못박아둬서 자유도가 없다.

**입력 데이터**

| 필드 | 소스 | 필수 |
| --- | --- | --- |
| 후보 입지 좌표 | 지오코딩 결과 (3-1 재사용) | Y |
| 후보 점포 전용면적(㎡) | 담당자 입력 | Y |
| 기존 가맹점 좌표 리스트 | 매장 마스터 DB | Y |
| 기존 가맹점 직전사업연도 매출액 | 매출 DB (더미/실데이터) | Y |
| 기존 가맹점 전용면적 | 매장 마스터 DB | Y |
| 기존 가맹점 영업 개시일 | 매장 마스터 DB | Y |

**처리 로직 (법정 순서, 임의 변경 불가)**
```
1. 후보 입지 기준 전 매장 직선거리 계산 (Haversine)
2. 직전사업연도 영업기간 6개월 미만 매장 제외
3. 거리순 정렬 → 최인접 5개 매장 선정
4. 각 매장 매출환산액 = 직전사업연도 매출액 ÷ 전용면적(㎡당 매출)
5. 매출환산액 최댓값 1개, 최솟값 1개 제외 → 나머지 3개만 사용
6. 예상매출액 최저치 = 3개 중 최솟값 매출환산액 × 후보점포 전용면적
7. 예상매출액 최고치 = 3개 중 최댓값 매출환산액 × 후보점포 전용면적
8. 검증: 최고치 ÷ 최저치 > 1.7 → 시스템 경고, 재산정 필요 (5개 후보군 재검토)
```

**출력**: 예상매출액 산정서 (서면 양식), 산정 근거 첨부(사용 매장 익명 코드 A~E, 매출환산액, 제외 매장 및 제외 사유)

**이력관리**: 산정일시·담당자·승인자·사용된 5개 매장 목록 스냅샷을 5년간 보관. 4단계(최인접 5개 선정)는 수동 오버라이드 불가 — 실제 판례에서 손해배상 사유가 된 지점이 "임의로 유리한 매장을 골라 최저액을 부풀린 것"이었기 때문.

### 1-5. 3-3. 인근가맹점 현황문서 (법정 서면)

1. 후보 입지 기준 반경 N km 내 동일 브랜드 매장 필터링
2. 매장명, 주소, 개점일, 직선거리 리스트업

**출력**: 인근가맹점 현황문서 (표 형식 서면) — 별도 계산 로직 없이 조회·필터링만 수행.

### 1-6. 3-4. 창업비용·ROI 시뮬레이션

**입력**: 표준 비용 템플릿(가맹비, 교육비, 인테리어, 설비, 초도물품비, 보증금 등) — HQ가 사전 등록

- 3-2에서 산출된 예상매출액 범위(최저~최고)를 그대로 재사용해 3개 시나리오 자동 생성

| 시나리오 | 매출 기준 |
| --- | --- |
| 보수 | 예상매출액 최저치 |
| 기본 | 산정서상 대표값(3개 매출환산액 평균 적용) |
| 낙관 | 예상매출액 최고치 |

- 시나리오별 영업이익 = 매출 × (1 − 원가율 − 인건비율 − 임차료율 − 로열티율)
- 손익분기점(BEP), 투자회수기간(개월) = 총 투자비 ÷ 월평균 영업이익 자동 계산

두 문서(산정서·ROI) 간 매출 가정이 어긋나면 그 자체로 "허위·과장" 소지가 되므로, 3-2의 법정 산정 범위를 그대로 재사용하는 게 핵심 설계 포인트.

### 1-7. 3-5. 상담용 슬라이드 생성

3-1~3-4 산출물을 템플릿에 자동 매핑해 발표용 슬라이드 5장 생성. 별도 계산 로직 없음(렌더링 기능).

### 1-8. 연계 기능(기존 MVP 재사용)

| 연계 기능 | 재사용 내용 |
| --- | --- |
| 매출 원인분석 | 유사 상권 매칭 로직 참고 (단, 3-2는 별도 법정 로직으로 독립 구현) |
| 지원사업 매칭·안내 | 후보 입지 지역/업종 기준 정부지원사업 리스트 그대로 재사용 |
| 매장 마스터 DB | 좌표, 면적, 매출, 영업개시일 — 신규 필드 추가 필요(좌표, 전용면적) |

### 1-9. 예외 처리

| 상황 | 처리 |
| --- | --- |
| 반경 내 동일 브랜드 매장 5개 미만 | 산정서 자동생성 불가 → 수동 산정 필요 안내 |
| 최고/최저 1.7배 초과 | 경고 후 재산정 유도, 강제 진행 불가 |
| 영업기간 6개월 미만 매장뿐인 상권 | 해당 지표 제외 안내 |

## 2. 도메인 점검 — 원안에서 무엇이 맞고 무엇이 위험했나

### 맞는 부분(그대로 유지)
- 예상매출액 산정서·인근가맹점 현황문서를 법정 서면으로 분리하고 계산 순서를 고정한 것(1-4) — 가맹사업법 시행령이 계산 방식을 못박아둔 게 맞고, 신규 가맹점주(계약 체결 전)에게만 발생하는 의무. 재계약 가맹점주에게는 이 서면 자체가 법적으로 발생하지 않음 → 신규/재계약을 분리하는 방향이 정확히 이 법적 차이를 따라간 것.
- 최고/최저 1.7배 초과 시 강제 재산정, 5개 매장 임의선정 불가 — 실제 손해배상 판례(유리한 매장만 골라 최저액 부풀리기)를 반영한 설계, 유지.

### 위험하거나 빠진 부분

**(1) "영업지역(exclusive territory)" 개념 부재** — 원안의 3-1은 반경 내 동일 브랜드 매장 수를 "적합/주의/부적합" 등급으로만 다뤘다. 그러나 2013년 가맹사업법 개정 이후 가맹계약에는 영업지역을 명시하도록 법적으로 의무화되어 있고(§5-2), 이미 있는 가맹점의 영업지역과 겹치는 자리에는 본사가 임의로 신규 출점을 승인할 수 없다(가맹점 동의 없이는 축소 불가). 이건 "위험도가 높아지는 지표"가 아니라 계약상 하드 블록일 수 있다. 등급표에 녹여 넣지 말고 별도 게이트로 분리해야 한다.

**(2) 신규 가맹점주 vs 본사 희망 상권의 "조율" 프로세스 부재** — 원안은 후보 입지 1곳을 입력받아 그 자리를 평가하는 구조였다. 실제로는 예비 점주가 원하는 지역과 본사가 원하는 확장 전략(출점 지도)이 다를 수 있고, 최종 입지는 본사의 출점심의를 거쳐 확정된다.

**(3) 재계약 가맹점주에게 "조건을 조정해준다"는 전제가 법적으로 위험** — 가맹사업법 §13은 가맹점주에게 계약갱신요구권을 부여한다(총 10년 한도, 최초 계약일로부터). 본사가 갱신을 거절할 수 있는 사유는 가맹금 미납·중대 계약위반 등으로 법에 열거되어 제한되어 있다. "재계약 조항을 각 가맹점주에 맞게" 만드는 상담자료가 본사가 일방적으로 조건을 바꿔 제시하는 근거 자료로 오인되면 갱신거절권 남용 소지가 생긴다.

**(4) 재계약 트랙을 처음부터 새로 설계할 필요가 없음** — 이 조직에 이미 "폐점 재계약 리스크 조기경보 모델" 프로젝트가 정확히 이 목적(개별 가맹점 폐업확률 → 예방조치 결정 + 재계약 조항 설계, SHAP 기반 "위험요인 → 조치/조항" 가이드)으로 완료돼 있다(3절에 전체 내용 인라인). 재계약 트랙은 새 로직을 만들지 말고 이 모델의 산출물(스코어 + SHAP 가이드 표)을 상담자료 템플릿에 매핑하는 렌더링 계층으로 설계하는 게 맞다 — 계산을 두 번 만들면 숫자가 어긋날 때 "허위·과장" 리스크가 배가된다.

**(5) 동일 상권을 여러 예비 점주가 동시에 희망할 때의 우선순위 규칙 없음** — 선점 규칙(선착순 상담 접수일 기준 등)이 없으면 상담 단계에서부터 내부 분쟁 소지.

## 3. 재사용 대상 — 폐점 재계약 리스크 조기경보 모델 (전체 인라인)

재계약 트랙이 그대로 가져다 쓸 프로젝트. 로컬 코드 경로: `C:\Users\yooyj\projects\closure-risk-model` (vault에는 코드 복사하지 않음, 이 경로만 참조).

### 3-1. 목적
프랜차이즈 본사가 가맹점 관리 차원에서 개별 가맹점의 폐업확률을 파악하고, 이를 근거로 (1) 폐업을 막기 위한 예방조치를 정하고 (2) 재계약 시 참고할 계약 조항을 설계하는 데 쓰기 위한 모델. 단순 예측 정확도 자체보다 어떤 요인이 위험을 높이는지 해석 가능한 형태로 제시하는 것이 핵심 요구사항.

### 3-2. 타겟 정의
브랜드×연도 단위 `discontinuation_rate = (계약종료수+계약해지수) / 연초가맹점수` (공정거래위원회 가맹사업 정보공개서 `1112` 가맹점 변동 현황 기준 실측치, 1.0으로 클립). **개별 가맹점 단위가 아니라 브랜드 단위 집계 실측**이라는 점이 핵심 한계(9절 참고).

### 3-4. 최종 모델 성능
- 데이터: `data/interim/brand_modeling_dataset.csv`, 시간 기반 홀드아웃(2024년 학습 n=1,931 / 2025년 검증 n=1,892)
- 모델: scikit-learn `HistGradientBoostingRegressor`(LightGBM 대체 — 이 환경의 애플리케이션 제어 정책이 LightGBM 네이티브 DLL 로딩을 차단해 대체), `sample_weight=sqrt(연초가맹점수)`, `l2_regularization=10`
- **RMSE 0.2333** vs. 평균값 예측 베이스라인 0.2386 — 베이스라인을 이김(이 프로젝트에서 유일하게 베이스라인을 이긴 결과)
- **MAE 0.1730**
- **Spearman 순위상관 0.1694** — 이 프로젝트 최고치

**솔직한 평가**: 개선됐지만 여전히 절대적으로는 약한 모델. 순위(어느 브랜드가 상대적으로 더 위험한지)를 어느 정도 분별하고 점 추정도 근소하게 낫지만, Spearman 0.169는 "잘 맞는다"고 보기엔 부족한 수준. 아래 SHAP 분석과 가이드 표는 "정밀한 점수"가 아니라 **"어떤 방향의 요인이 위험과 연관되는지"** 정도의 방향성 지표로 해석해야 한다.

### 3-6. 위험요인 → 예방조치/재계약 조항 가이드 표

개별 점포 맞춤이 아니라 **피처 카테고리 단위**로 "이 요인이 높을 때 일반적으로 검토할 예방조치/재계약 조항"을 정리한 것. 각 항목의 신뢰도(SHAP 근거 강도)를 함께 표기 — 신뢰도가 낮은 항목은 참고용 가설로만 취급.

| # | 위험요인 카테고리 | 근거(SHAP) | 예방조치 | 재계약 조항 |
|---|---|---|---|---|
| 1 | 업종 구조적 위험(같은 업종 내 다른 브랜드들의 해지율이 높음) | 강함(1위, 압도적) | 업종 트렌드 정기 모니터링, 업종 내 경쟁·수요 변화에 대한 조기 경보 체계 구축, 복수 업종 포트폴리오/업종 전환 상담 제공 | 업종 변경 시 계약 승계·조건 조정 조항 명확화, 업종 base rate가 높은 브랜드는 최소 매출 기준 재검토 주기를 단축 |
| 2 | 초기 투자·비용 부담(이행보증금/인테리어비용/기타가맹비용/보증금/평당인테리어/교육비/초기비용총액 등) | 중간(개별로는 약하나 합산 비중이 1위 다음으로 큼) | 신규 가맹 전 초기비용 회수 기간 시뮬레이션 제공, 이행보증금·인테리어 부담이 큰 가맹점 대상 임대료/비용 재협상 지원 프로그램 우선 검토 | 초기비용 회수 미달 시 계약 조건 유예/분할 조항, 인테리어 재투자 주기와 갱신 시점을 연동하는 조항 검토 |
| 3 | 경쟁밀도(반경 250m/500m 내 동일업종 점포 수) | 중간(처음으로 유의미한 지리적 신호) | 경쟁 점포가 밀집한 지역의 가맹점 대상 포지셔닝 차별화 지원, 신규 출점 시 경쟁밀도 사전 검토 | 반경 내 동일업종 신규 출점 제한(상권보호) 조항 강화, 경쟁밀도 급변 시 갱신조건 재검토 트리거 마련 |
| 4 | 업종 분류(업종중분류/대분류 자체 특성) | 중간 | 업종별 표준 리스크 관리 템플릿 차등 적용(외식/도소매/서비스 업종 특성에 맞는 지원책) | 업종별 표준 재계약 조항 템플릿 마련(업종 특성 반영) |
| 5 | 브랜드 업력(신생 브랜드일수록) | 약함 | 개업 초기(업력 짧은 브랜드) 밀착 지원 프로그램(운영 컨설팅, 초기 마케팅 지원) | 브랜드 성장 단계별 갱신조건 차등화, 초기 몇 년은 완화된 조건 적용 검토 |

이 리포트에서 다루지 못한 카테고리(데이터 미확보로 제외): 매출·유동인구 추이, 임대료 부담, 가맹본부 재무건전성·법위반 이력(매핑 시도했으나 커버리지 2~3%로 검증 불가). 경쟁밀도는 sbiz 단일 시점 스냅샷이라 시계열 변화는 반영하지 못함.

### 3-7. 검증 요약
- decile 분석: valid를 예측 위험도 10분위로 나누면 실측 해지율이 단조감소(1분위 0.251 → 10분위 0.091, 상하위 10% 간 2.75배 차이) — 극단 그룹 분리력은 실용적 수준.
- **업종별 편차 큼**: 서비스 업종은 Spearman 0.02로 순위분별력이 거의 없음(전체 평균 0.169가 이 편차를 가림). 대형 브랜드(≥10점)는 0.227로 더 좋음.
- **재계약 트랙 설계 시 반드시 반영**: 종합 지표만 보고 "이 모델이 어디서나 똑같이 작동한다"고 오해하면 안 됨 — 서비스 업종 대상 상담자료에는 "정량 예측 신뢰도 낮음" 경고를 자동 표기해야 한다.

### 3-8. 캘리브레이션 및 추론 파이프라인 사용법
- **캘리브레이션**(`src/models/calibration.py`): valid를 반으로 나눠(n=946/946) 한쪽에 Isotonic Regression을 적합, 다른 쪽 홀드아웃으로 검증. 홀드아웃 MAE가 0.1767→0.1754로 개선.
- **추론 파이프라인**(`src/pipeline.py`): 브랜드 피처 dict를 입력받아 raw/calibrated 위험 스코어를 출력하는 CLI. 실행: `python -m src.pipeline --input-json <파일>`. `induty_mclas_nm`+`year`만 있으면 업종 피어평균을 자동 조회해 채워준다.

**입력 예시** (`docs/pipeline_input_example.json`):
```json
{
  "year": 2025,
  "deposit_amt": 13000,
  "diff_franchise_fee": 5000,
  "interior_cost": 33000,
  "unit_area_interior_cost": 1800,
  "biz_assurance_amt": 2000,
  "education_fee": 3300,
  "etc_fee": 6000,
  "franchise_fee_total": 8000,
  "total_initial_cost": 46500,
  "first_contract_years": 2,
  "renewal_contract_years": 1,
  "brand_age_years": 5,
  "avg_competitors_250m": 6,
```

(단위: 비용은 천원, 연수는 년. 모르는 값은 키를 생략하면 NaN 처리됨)

### 3-9. 한계 (재계약 상담자료에 반드시 고지)
1. **브랜드 단위이지 개별 가맹점 단위가 아님** — 개별 점포 단위 예측은 이 모델로 완전히 달성되지 못함. FTC 데이터가 점포별 원자료를 COUNT 집계로만 노출해 개별 점포 데이터를 구조적으로 확보할 수 없었음.
2. **예측력이 약함** — RMSE는 베이스라인을 이겼지만 근소한 차이, Spearman 0.169도 절대 정확도로는 약한 수준. 가이드 표는 "정답"이 아니라 방향성 참고 자료.
3. **업종별 신뢰도 편차** — 서비스 업종은 가이드 표를 그대로 적용하면 안 됨.
4. **표본 크기** — 학습 1,931건/검증 1,892건, 브랜드의 74%가 가맹점 10개 미만이라 타겟 자체의 분산 상당 부분이 소표본 노이즈.
5. **데이터 공백** — 유동인구/임대료(지방 커버리지 없음), 가맹본부 재무/법위반(매핑 10%만 성공), 매출(커버리지 1% 미만).
6. **프록시 특성** — 등록취소·업종 피어평균·경쟁밀도(단일 시점) 등 일부 보조 신호는 근사치.
7. **브랜드↔점포 매칭의 불확실성** — 경쟁밀도 계산에 쓴 브랜드-점포 매칭이 상호명 문자열 부분일치 기반.
8. **캘리브레이션의 낮은 해상도** — 홀드아웃 n=946 수준에서 Isotonic 계단함수가 거칠어 다른 raw score가 같은 보정값으로 뭉개지는 경우 있음.

### 4-1. 신규 가맹점주 트랙 — 추가 기능: 희망 상권 vs 본사 희망 상권 조율

```
1. 예비 점주 희망 주소 입력 → 지오코딩
2. 희망 주소 반경 M km 내에서 후보지 그리드 생성
   (1-3 상권 스코어카드 로직을 각 격자점에 반복 적용)
3. "영업지역 침해" 게이트 통과한 후보만 남김
4. 남은 후보를 1-3 등급(적합/주의/부적합) + 본사 확장전략 우선순위로 랭킹
5. 상위 N개를 "예비 점주 희망지 인근 추천 입지"로 제시 → 예비 점주·본사 담당자가 최종 후보 1곳 합의
6. 합의된 1곳에 대해서만 1-4(예상매출액 산정서)·1-5(인근가맹점 현황문서) 실행
```

이후 1-4~1-7(예상매출액 산정서, 인근가맹점 현황문서, ROI 시뮬레이션, 슬라이드)은 원안 로직 그대로 유지 — 법정 계산이라 자유도가 없고 원안 설계가 맞다.

**3·4단계 fallback(데이터 미확보 상태에서도 막히지 않도록 확정)**

| 단계 | 이상적 데이터 | 지금 쓸 fallback | 비고 |
| --- | --- | --- | --- |
| 3(영업지역 게이트) | 계약서상 영업지역 폴리곤/좌표 | 1-4에서 이미 쓰는 "최인접 5개 매장" Haversine 로직 재사용 → 반경 500m 내 동일 브랜드 매장 존재 시 자동 차단(등급 아님, 하드 스킵) | `ponytail: 반경 근사 게이트, 계약서 영업지역 데이터 확보되면 폴리곤 기반 정확 판정으로 교체` |
| 4(본사 확장전략 우선순위) | HQ가 사전 등록한 타겟 상권 리스트 | 리스트가 비어있으면 이 가중치 항목을 0으로 두고 1-3 등급만으로 랭킹 | 입력 없으면 항목 생략은 정상 동작, 기능이 죽지 않음 |

이 fallback 덕분에 "계약서 영업지역 데이터가 시스템에 구조화돼 있는지"를 확인받기 전에도 설계·개발을 시작할 수 있다. 실제 데이터가 들어오면 3행의 로직만 교체하면 되고, 나머지 파이프라인(그리드 생성·랭킹·합의 절차)은 그대로 간다.

**동시성 규칙**: 동일 격자점이 서로 다른 상담 건에서 상위 후보로 겹칠 경우, 상담 접수일시가 빠른 건을 우선하고 후순위 건에는 "해당 입지는 타 상담 건과 중복, 대안 후보 제시" 안내를 자동 표기.

## 5. 매장 마스터 DB 필드 확인 (2026-07-31 실측)

closure-risk-model 저장소가 쓰는 공공데이터(sbiz 상가업소 데이터·FTC 정보공개서)를 직접 열어 확인:

| 필드 | 공공데이터에 개별 매장 단위로 존재하는가 |
| --- | --- |
| 좌표(위도/경도) | 있음(sbiz 상가업소 데이터 `경도`/`위도` 컬럼) — 주소만 있어도 지오코딩으로 즉시 파생 가능 |

| 영업개시일 | 없음 — FTC 공개데이터는 브랜드 단위 가맹사업개시일(`jng_biz_strt_date`)만 제공, 개별 매장 실제 개점일은 계약서/현장 데이터에만 존재 |

## 6. 개발 전략 — 가상 시나리오로 개발, 실전은 실데이터로 스왑

필드 유무 확인·backfill을 기다리지 않고 지금 개발을 시작하는 방식:

1. `store_lat`, `store_lon`, `store_area_sqm`, `store_open_date` 4개 필드로 매장 마스터 스키마를 지금 확정
2. 매장 조회 인터페이스를 함수 하나(`get_nearby_stores(brand, lat, lon, n=5) -> list[dict]`)로 고정 — 1-3~1-6 로직은 전부 이 함수의 반환값만 사용하고 데이터 출처는 모름
3. 개발·테스트 단계: 이 함수를 실제 분포와 비슷하게 만든 가상 매장 10~20개(면적 20~150㎡, 매출 정규분포, 좌표는 실제 상권 좌표에 지터 추가)로 채운 mock 구현으로 대체
4. 실전 전환: 같은 함수 시그니처로 내부 DB 커넥터 구현체 하나만 교체 — 1-3~1-6 로직은 한 줄도 안 바뀜

`ponytail: mock 매장 마스터, 실제 매장 마스터 DB 연동 확정되면 get_nearby_stores 구현체만 교체`

**실행 검증 완료(2026-07-31)**: 위 전략대로 mock 매장 12개 + 1-4절 로직(6개월 미만 제외 → 최인접 5개 → 최댓값/최솟값 제외 3개 → 최저/최고 산정 → 1.7배 검증)을 실제로 구현·실행해 정상 동작 확인.

```python
import math, random
from datetime import date, timedelta
random.seed(7)

def haversine_m(lat1, lon1, lat2, lon2):
    r = 6371000
    p1, p2 = math.radians(lat1), math.radians(lat2)
    dp, dl = math.radians(lat2 - lat1), math.radians(lon2 - lon1)
    a = math.sin(dp/2)**2 + math.cos(p1)*math.cos(p2)*math.sin(dl/2)**2
    return 2 * r * math.asin(math.sqrt(a))

def _mock_store_master(brand, center_lat, center_lon, n=12):
    today = date(2026, 7, 31)
    return [{
        "store_id": f"{brand}-{i:03d}", "brand": brand,
        "lat": center_lat + random.uniform(-0.02, 0.02),
        "lon": center_lon + random.uniform(-0.02, 0.02),
        "area_sqm": round(random.uniform(20, 120), 1),
        "open_date": today - timedelta(days=random.randint(60, 365*5)),
        "last_year_sales": round(random.uniform(1.5e8, 6e8)),
    } for i in range(n)]

def get_nearby_stores(brand, lat, lon, n=5):
    """실전 전환 지점: 이 함수 내부만 실제 매장 마스터 DB 쿼리로 교체."""
    ref_date = date(2026, 7, 31)
    eligible = [s for s in _mock_store_master(brand, lat, lon)
                if (ref_date - s["open_date"]).days >= 183]
    for s in eligible:
        s["dist_m"] = haversine_m(lat, lon, s["lat"], s["lon"])
    return sorted(eligible, key=lambda s: s["dist_m"])[:n]

def calc_expected_sales(brand, lat, lon, candidate_area_sqm):
    nearby = get_nearby_stores(brand, lat, lon, n=5)
    if len(nearby) < 5:
        return {"status": "산정서 자동생성 불가 (반경 내 5개 미만)"}
    for s in nearby:
        s["sales_per_sqm"] = s["last_year_sales"] / s["area_sqm"]
    ranked = sorted(nearby, key=lambda s: s["sales_per_sqm"])
    used = ranked[1:-1]  # 최댓값 1개, 최솟값 1개 제외
    low = min(s["sales_per_sqm"] for s in used) * candidate_area_sqm
    high = max(s["sales_per_sqm"] for s in used) * candidate_area_sqm
    ratio = high / low
    return {
        "status": "재산정 필요 (1.7배 초과)" if ratio > 1.7 else "정상 산정",
        "used_stores": [s["store_id"] for s in used],
        "excluded_stores": [ranked[0]["store_id"], ranked[-1]["store_id"]],
        "expected_sales_low": round(low), "expected_sales_high": round(high),
        "ratio": round(ratio, 3),
    }

def demo():
    result = calc_expected_sales("본죽", 37.5665, 126.9780, candidate_area_sqm=45.0)
    assert result["status"] in ("정상 산정", "재산정 필요 (1.7배 초과)")
    assert result["expected_sales_low"] <= result["expected_sales_high"]
    assert len(result["used_stores"]) == 3
    print(result)

if __name__ == "__main__":
    demo()
```

실행 결과(본죽, 서울시청 좌표, 후보면적 45㎡):


### 5절 필드 확인 — 완료 (2026-08-05, 팀 레포 직접 클론해 확인)

"팀 내부 확인이 필요"하다고 남겨뒀던 항목 중 매장 마스터 DB 필드는 `https://github.com/OhDomi/OhDomiSpring.git`을 직접 클론해서 `schema.sql`/`data.sql`/API(`StoreController.java`)를 열어 확답을 얻었다(Slack 등 팀 채널 없이 코드로 직접 확인).

**검증 방법**: MySQL 대신 로컬 H2(인메모리, MySQL 호환 모드)로 Spring Boot 앱을 실제로 기동해 `GET /api/stores`/`GET /api/stores/{id}/sales-summary`를 실제로 호출·응답 확인(팀 저장소의 `build.gradle`은 검증 후 원상복구, 커밋 없음).

**코드 반영**: `src/new_franchisee_packet.py`에 `OHDOMI_API_BASE_URL` 환경변수로 켜지는 실 연동 경로(`_live_store_master()`) 추가 — 기본은 여전히 mock(하위호환). 실 연동 시 `area_sqm`은 확인된 대로 항상 `None`이고, `calc_expected_sales()`가 이를 감지해 "산정서 자동생성 불가(전용면적 없음)"를 명시적으로 반환(0으로 나누기 등 조용한 오류 대신). **브랜드 필터링은 실 DB에서 불가능**(필드 자체가 없음) — `brand` 인자는 표시용으로만 남고 전체 매장이 후보가 됨.

### 남은 진짜 블로커
- **전용면적** — DB에 신규 필드 추가하거나 계약서 원본에서 backfill해야 법정 예상매출액 산정서가 실제로 완성됨(현재는 여기서만 막혀 있음)
- **브랜드 개념 부재** — 예비창업자 상담 시나리오 자체가 "여러 브랜드 중 후보 선택"을 전제하는데, OhDomiSpring은 단일 브랜드 시스템이라 신규 트랙을 실서비스로 붙이려면 `stores`에 브랜드 필드를 추가하거나(다른 브랜드 매장도 이 DB에 들어온다는 뜻이라 스키마 설계 자체가 커짐), 이 기능의 전제("예비창업자가 비교할 여러 브랜드")를 팀과 다시 확인해야 함
- 계약서상 "영업지역" 구조화 데이터, 본사 "희망 상권 지도" 리스트는 아직 미확인(둘 다 fallback으로 개발은 막히지 않음)
