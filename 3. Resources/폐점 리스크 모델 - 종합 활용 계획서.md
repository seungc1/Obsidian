# 폐점·재계약 리스크 조기경보 모델 — 종합 활용 계획서

[[1. Projects/폐점 재계약 리스크 조기경보 모델]]을 프랜차이즈 본사의 실제 가맹점 관리 업무에 어떻게 넣을지 정리한 계획서. 모델 자체의 성능·한계는 [[3. Resources/폐점 리스크 모델 - 최종 보고서 (팀 공유용)]] 참고 — 이 문서는 "그래서 어떻게 쓸 것인가"에 집중한다.

---

## 1. 기본 원칙 (모든 활용의 전제)

1. **순위 참고 도구이지, 자동 판정 시스템이 아니다.** "이 매장 폐업확률 73%" 식으로 절대값을 신뢰하지 않는다.
2. **최종 조치는 항상 사람이 결정한다.** 재계약 거절, 임대료 조정, 계약 조항 삽입 등은 모델이 자동 실행하지 않는다 — 법적·평판 리스크가 크다.
3. **커버리지에 따라 신뢰 수준을 다르게 취급한다.** 서울 매장(v2)은 정밀 진단, 그 외 지역(v1)은 참고 신호 정도로만.
4. **정량 점수보다 우선순위 리스트로 노출한다.** 절대 임계값(예: "70% 이상 위험")이 아니라 "이번 분기 상위 N개" 형태로.

---

## 2. 단계별 롤아웃 (3단계 파일럿 → 확대 → 정착)

### Phase 1 — 파일럿 (1~2개 분기, 소수 브랜드/담당자)

- **대상**: **김가네로 확정(2026-08-05)** — 분식 프랜차이즈, 전국 424개 가맹점(대규모 요건 충족), 실측 해지율 2.23%로 안정적, 업력이 길어 재계약 트랙 대표 사례로 적합. v1으로 대규모 프랜차이즈 197개를 실제 스코어링해 비교한 결과 및 v2로 한식 프랜차이즈군과 비교한 결과를 근거로 선정
- **범위**: v2 우선순위 리스트만 제공(2x2 결합 판단, 조항 추천은 아직 미노출 — 검증 우선)
- **목표**: "이 리스트가 실제로 담당자의 판단과 얼마나 일치하는가"를 정성적으로 확인
- **산출물**: 분기말 "예측 상위 리스트 vs 담당자 체감 위험도" 비교 메모
- **파일럿 데이터 확보 현황(2026-08-05)**: 김가네 실제 매장 주소·좌표는 sbiz 공공데이터에서 정확 매칭(상호명 "김가네"/"김가네김밥")으로 전국 216개(서울 88개) 확보 완료 — `data/interim/kimgane_real_stores_216.csv`. 개점일·전용면적·실제 매출은 공공데이터로 확보 불가(계약서/내부 매장관리 시스템 필요) — OhDomi 팀 쪽 확인 요청함(아래 10절 및 [[1. Projects/폐점 재계약 리스크 조기경보 모델]] 진행 로그 참고)

### Phase 2 — 확대 (파일럿 검증 후, 전체 브랜드)

- v1(전국)까지 전체 브랜드로 확대, 서울 외 지역은 "업종 동향 알림" 수준으로 노출
- 조항 추천 기능을 **법무팀 검토용**으로 시범 도입(직접 담당자에게는 아직 미노출)
- 분기별 배치 자동화(3절 참고) 정식 가동

### Phase 3 — 정착 (Phase 2 안정화 후)

- 조항 추천을 가맹관리 담당자 화면에도 노출(단, "법무 검토용 초안" 라벨 유지)
- 피드백 루프(6절) 데이터가 1년 치 쌓이면 캘리브레이션 재검증 → 신뢰도 표시 고도화

## 3. 운영 프로세스 (분기별 배치)

```
[분기별 데이터 갱신]
  ├─ v2 데이터(서울 열린데이터광장) — 분기 갱신 주기에 맞춰 자동 재수집
  └─ v1 데이터(FTC 정보공개서) — 연 1회 갱신(공시 주기)
        ↓
[재학습 + 재스코어링]
  ├─ src/models/train.py (v1) / train_seoul_closure.py (v2)
  └─ 전체 브랜드/매장 재스코어링 → src/models/score_distributions.py로 백분위 갱신
        ↓
[우선순위 리스트 생성]
  ├─ 서울 매장: src/combine_scores.py → 2x2 매트릭스(고위험/업종위험/입지위험/안전)
  └─ 서울 외: v1 백분위 기준 "업종 동향 주의" 목록
        ↓
[담당자 검토 + 필요 시 조항 추천 조회]
  └─ src/clause_recommendation.py → 법무 검토용 초안 (사람이 최종 결정)
        ↓
[조치 실행] → 사람이 판단 (자동 실행 없음)
        ↓
[결과 기록] → 6절 피드백 루프로 다음 분기 검증에 반영
```

## 4. 조직별 역할

| 역할            | 무엇을 하는가                                  | 무엇을 하면 안 되는가                           |
| ------------- | ---------------------------------------- | -------------------------------------- |
| **데이터팀**      | 분기별 배치 실행, 모델 재학습, 성능 모니터링(6절)           | 점수만 보고 조치를 대신 결정                       |
| **가맹관리 담당자**  | 우선순위 리스트로 이번 분기 방문·점검 대상 선정, 조항 추천 초안 참고 | 리스트 순위를 절대 확률로 취급, 조항 문구를 검토 없이 그대로 발송 |
| **법무팀**       | 조항 추천 초안을 실제 계약 문구로 검토·수정                | 모델이 생성한 문구를 무수정 채택                     |
| **경영진/의사결정자** | 분기별 요약 리포트(고위험 매장 수, 트렌드) 확인             | 개별 매장 재계약 여부를 점수 하나로 결정                |

---

## 5. 무엇을 자동화하고, 무엇을 하면 안 되는가

**자동화 가능**
- 데이터 수집·재학습·재스코어링(분기 배치)
- 우선순위 리스트 생성 및 담당자에게 배포
- 조항 추천 "초안" 생성(사람이 검토한다는 전제하에)
- 방향 확인 경고(`⚠️ 방향 확인 필요`) 자동 표시

**절대 자동화 금지**
- 재계약 거절/갱신 여부 결정
- 임대료·계약조건 변경 실행
- 조항 추천 문구를 검토 없이 계약서에 삽입
- 특정 임계값 초과 시 자동 알림 발송(오탐 시 신뢰도 손상 위험 — 사람이 우선순위 리스트를 보고 판단하는 방식 유지)

---

## 6. 피드백 루프 — 다음 검증 단계

지금까지는 "과거 데이터 홀드아웃" 검증까지만 됐다. 실제 운영에 들어가면 다음을 반드시 추적한다:

1. **분기마다** 지난 분기 "고위험" 리스트에 올랐던 매장 중 실제로 문제(매출 급감, 재계약 실패, 폐업)가 생긴 비율 기록
2. 이 실측 결과를 캘리브레이션(`calibration.py`) 재적합에 반영 — 지금은 "잠정 캘리브레이션" 상태
3. 조항 추천이 실제로 채택된 사례와 그 결과(재계약 성사 여부 등)를 별도로 기록해, 추후 조항 추천 품질 자체를 검증하는 데이터로 축적
4. v1의 서비스 업종, v2의 근사매핑 브랜드처럼 이미 알려진 저신뢰 구간은 피드백 데이터가 쌓여도 별도로 취급(전체 평균에 묻히지 않게)

---

## 7. 성공 지표 (무엇을 보고 "잘 되고 있다"고 판단할까)

- **채택률**: 담당자가 우선순위 리스트를 실제로 업무에 참고한 비율
- **적중도**: 고위험으로 분류된 매장 중 실제 문제가 발생한 비율 vs 안전 분류 매장의 문제 발생률 (격차가 클수록 모델이 유효)
- **조치 선행성**: 문제가 실제로 불거지기 전에 얼마나 일찍 리스트에 잡혔는가(리드타임)
- **조항 추천 채택률 및 방향 확인 경고 발생 빈도**: 경고가 너무 자주 뜨면 `risk_clause_map.py`의 방향 가정 자체를 재검토해야 함

## 8. 일정 감각 (참고용, 확정 아님)

| 단계 | 기간 | 주요 산출물 |
|---|---|---|
| Phase 1 파일럿 | 1~2개 분기 | 담당자 체감 검증 메모 |

| Phase 3 정착 | 1년 치 피드백 누적 후 | 재검증된 캘리브레이션, 조항 추천 신뢰도 지표 |

## 9. 프론트엔드 페이지 구성 (2026-08-04 — ⚠️ 아래 정정 참고, "로컬 도구"로 범위 축소)

**⚠️ 2026-08-04 정정**: 처음엔 "이 프로젝트는 팀원 없이 단독 진행 중"이라고 판단해 화면 구성을
직접 확정하고 API+정적 페이지까지 구현했으나, 같은 날 작성된
[[3. Resources/OhDomi 프로젝트 - 팀 저장소 구성 및 아키텍처]]를 보면 **실제로는 팀 저장소
5개(OhDomiReact/OhDomiSpring/hygiene_ai/OhDomiAI/closure-risk-model)가 있고, "프론트 화면
구성"은 이미 팀원이 `OhDomiAI` 레포에서 설계·구현까지 끝내둔 상태**였음(Spring
`risk-patch/RiskController.java`의 `GET /latest`/`POST /refresh`, React
`react-patch/AdminRiskPrediction.tsx`의 SHAP 요인 카드 UI, 둘을 잇는 OhDomiAI
`service/main.py`의 `POST /risk-score`). 병합만 안 됐을 뿐 화면 구성 자체는 미정이 아니었음
— 유일한 실제 블로커는 스키마 결정(기존 운영지표 `risk_assessments` vs 모델 기반 스키마)이지
프론트 레이아웃이 아니다. 즉 원래 "9절 미확정" 문제는 애초에 이미 풀려 있었고 몰랐을 뿐.

**그래서 아래 결정·구현은 "OhDomi 사이트 통합"이 아니라 별개의 로컬 개발/디버그 도구로
범위를 좁혀 유지한다** — 실제 사이트 통합은 위 OhDomiAI patch 쪽을 따라야 하고, 스키마
결정이 나면 그쪽을 병합하는 게 맞는 경로. 아래 API/화면은 이 모델 저장소만 갖고 빠르게
스코어를 눈으로 확인하고 싶을 때(팀 통합과 무관하게) 쓰는 용도로 남긴다.

**로컬 도구 구성**: 화면을 3구역으로 나눈 단일 대시보드.
1. **임박 재계약**: `filter_upcoming_renewals(within_days=180)`. 재계약 조항 협상 준비용.
2. **고위험 전체**: `combine_scores.py`의 `classification`(상위 25% 기준). 계약 시점과 무관하게 예방조치가 필요한 매장.
3. **예비창업자 상담 후보**(2026-08-04 prospect_packet.py 신설에 따라 추가 — 원래 안의 2구역에서 확장): `prospect_packet.py`의 브랜드/입지 수동+자동 로드를 그대로 노출.

1·2는 겹치는 매장을 "⚠ 동시 해당"으로 최상단 분리(원안의 검토안 그대로 채택).

**구현**:
- `src/api.py`(FastAPI, **로컬 개발용, OhDomi 사이트가 호출하는 API 아님**): `POST /dashboard/renewals`(구역 1+2), `POST /dashboard/prospects`(구역 3), `POST /packets/renewal`·`/packets/prospect`(문서 생성). 전부 기존 순수 함수(`combine_score`/`filter_upcoming_renewals`/`load_all_brand_candidates`/`apply_auto_location`/`generate_*_packet`)를 호출만 함 — 새 점수 로직 없음. OhDomiAI `service/main.py`(`/risk-score`, `/demo-stores`)와는 스키마·용도 둘 다 다른 별개 서비스 — 혼동 금지.
- `web/dashboard.html`: 빌드 도구 없는 순수 HTML+fetch 단일 페이지. 위 API를 실제로 눈으로 확인하는 참조 구현. `uvicorn src.api:app --reload` 후 브라우저로 열기.

**성능 이슈 발견·수정**: `renewals_dashboard`가 처음엔 "전체 레코드"와 "임박 부분집합"을 각각 다시 스코어링해 같은 레코드를 두 번 계산 — v2(주소 있는 매장)는 레코드당 지오코딩+sbiz 전체 스캔이 붙어 느려서(레코드 몇 건만 돼도 응답이 배로 늘어남), 레코드당 한 번만 계산해 재사용하도록 수정.

**검증**: 6개 API 테스트(mock 기반, 배선·구역 분류 로직만 검증) + 실제 uvicorn 서버를 띄워 `docs/renewal_batch_example.json`(실제 지오코딩·v1/v2 스코어링 포함)으로 3개 엔드포인트 전부 실제 데이터로 호출해 정상 응답 확인.

**실제 OhDomi 사이트 통합이 필요하면**: 이 절 대신 [[3. Resources/OhDomi 프로젝트 - 팀 저장소 구성 및 아키텍처]]의 "미해결 이슈"(스키마 결정 → `spring-patch`/`react-patch` 병합) 절을 따를 것.
