# 예비점주 상담자료 자동생성 - 기능 명세서 (신규·재계약 분리, v2)

원본 명세서(v1)를 검토한 도메인 점검 결과 + 사용자가 제안한 "신규/재계약 분리" 방향을 반영한 개정판. v1은 [[3. Resources/예비점주 상담자료 자동생성 - 기능 명세서 (v1)]]로 보존.

## 1. v1 도메인 점검 — 무엇이 맞고 무엇이 위험한가

### 맞는 부분 (그대로 유지)
- 예상매출액 산정서·인근가맹점 현황문서를 **법정 서면**으로 분리하고 계산 순서를 고정한 것(3-2) — 가맹사업법 시행령이 계산 방식을 못박아둔 게 맞고, 이건 신규 가맹점주(계약 체결 전)에게만 발생하는 의무. 재계약 가맹점주에게는 이 서면 자체가 법적으로 발생하지 않음 → **신규/재계약을 분리하자는 방향이 정확히 이 법적 차이를 따라간 것**.
- 최고/최저 1.7배 초과 시 강제 재산정, 5개 매장 임의선정 불가 — 실제 손해배상 판례(유리한 매장만 골라 최저액 부풀리기)를 반영한 설계, 유지.

### 위험하거나 빠진 부분

**(1) "영업지역(exclusive territory)" 개념 부재 — 3-1의 가장 큰 공백**
v1의 3-1은 반경 내 동일 브랜드 매장 수를 "적합/주의/부적합" **등급**으로만 다룬다. 하지만 2013년 가맹사업법 개정 이후 가맹계약에는 **영업지역을 명시하도록 법적으로 의무화**되어 있고(§5-2), 이미 있는 가맹점의 영업지역과 겹치는 자리에는 본사가 임의로 신규 출점을 승인할 수 없다(가맹점 동의 없이는 축소 불가). 즉 이건 "위험도가 높아지는 지표"가 아니라 **계약상 하드 블록(hard gate)**일 수 있다. 등급표에 녹여 넣지 말고 별도 게이트로 분리해야 한다.
→ 상권 스코어카드에 "영업지역 침해 여부"를 **판정 이전 단계의 통과/차단 체크**로 추가 필요 (기존 franchisee 계약서의 영업지역 데이터가 시스템에 있다는 전제 하에).

**(2) 신규 가맹점주 vs 본사 희망 상권의 "조율" 프로세스가 없었음**
v1은 "후보 입지 1곳"을 입력받아 그 자리를 평가하는 구조였다. 실제로는 예비 점주가 원하는 지역과 본사가 원하는 확장 전략(출점 지도)이 다를 수 있고, 최종 입지는 본사의 출점심의를 거쳐 확정된다. → 아래 3-1(신규 트랙)에서 "희망 지역 반경 내 후보지 랭킹" 기능으로 보강.

**(3) 재계약 가맹점주에게 "조건을 조정해준다"는 전제가 법적으로 위험**
가맹사업법 §13은 가맹점주에게 **계약갱신요구권**을 부여한다(총 10년 한도, 최초 계약일로부터). 본사가 갱신을 거절할 수 있는 사유는 가맹금 미납·중대 계약위반 등으로 **법에 열거되어 제한**되어 있다. v1 확장 아이디어처럼 "재계약 조항을 각 가맹점주에 맞게" 상담자료를 만들 때, 이게 **본사가 일방적으로 조건을 바꿔 제시하는 근거 자료**로 오인되면 갱신거절권 남용 소지가 생긴다.
→ 재계약 트랙 산출물에는 반드시 "이 가맹점이 법정 갱신요구권 대상인지(갱신 요구 가능 잔여 기간)"를 최상단에 표시하고, 조항 제안은 "권고안"이지 "강제 조건"이 아님을 명시하는 문구를 시스템이 강제해야 한다.

**(4) 재계약 트랙을 처음부터 새로 설계할 필요가 없음**
사용자가 "이전 데이터를 분석해서 재계약 조항이나 본사 조치점을 뽑는" 로직을 신규로 언급했는데, 이 저장소에 이미 [[1. Projects/폐점 재계약 리스크 조기경보 모델]]이 정확히 이 목적(개별 가맹점 폐업확률 → 예방조치 결정 + 재계약 조항 설계, SHAP 기반 "위험요인 → 조치/조항" 가이드)으로 완료돼 있다. 재계약 트랙은 새 로직을 만들지 말고 **이 모델의 산출물(스코어 + SHAP 가이드 표)을 상담자료 템플릿에 매핑하는 렌더링 계층**으로 설계하는 게 맞다 — 계산을 두 번 만들면 숫자가 어긋날 때 "허위·과장" 리스크가 배가된다(v1도 3-4에서 이 원칙을 정확히 지적했었음, 재계약 트랙에도 동일하게 적용해야 함).

**(5) 동일 상권을 여러 예비 점주가 동시에 희망할 때의 우선순위 규칙 없음**
"희망 지역 근처 최적 입지 추천"을 여러 상담 건에서 동시에 돌리면 같은 좋은 자리를 두 예비 점주에게 동시에 추천할 수 있다. 선점 규칙(선착순 상담 접수일 기준 등)이 없으면 상담 단계에서부터 내부 분쟁 소지.

## 2. 개정 구조 — 신규 / 재계약 분리

| 구분 | 신규 가맹점주 트랙 | 재계약 가맹점주 트랙 |
| --- | --- | --- |
| 발생 시점 | 계약 체결 전 (입지 상담) | 기존 계약 만료 접근 시 |
| 법적 근거 | 가맹사업법 §7, §9 (정보공개서 제공의무) | 가맹사업법 §13 (계약갱신요구권) |
| 법정 필수서류 | 예상매출액 산정서, 인근가맹점 현황문서 | 없음 (내부 상담자료) |
| 핵심 데이터 | 상권/유동인구/경쟁밀도 (신규 지오코딩) | 해당 매장의 과거 매출·계약·리스크 이력 |
| 재사용 모델 | 3-1 상권분석 로직 (v1 그대로) | [[1. Projects/폐점 재계약 리스크 조기경보 모델]] 산출물 |
| 산출물 성격 | 법정 서면 + 개인 맞춤 입지 추천 | 권고안 (강제 조건 아님, 갱신요구권 고지 필수) |

### 2-1. 신규 가맹점주 트랙

**추가 기능: 희망 상권 vs 본사 희망 상권 조율**

```
1. 예비 점주 희망 주소 입력 → 지오코딩
2. 희망 주소 반경 M km 내에서 후보지 그리드 생성
   (기존 3-1 상권 스코어카드 로직을 각 격자점에 반복 적용)
3. "영업지역 침해" 게이트 통과한 후보만 남김
4. 남은 후보를 3-1 등급(적합/주의/부적합) + 본사 확장전략 우선순위로 랭킹
5. 상위 N개를 "예비 점주 희망지 인근 추천 입지"로 제시 → 예비 점주·본사 담당자가 최종 후보 1곳 합의
6. 합의된 1곳에 대해서만 기존 3-2(예상매출액 산정서)·3-3(인근가맹점 현황문서) 실행
```

이후 3-2~3-5(예상매출액 산정서, 인근가맹점 현황문서, ROI 시뮬레이션, 슬라이드)는 v1 로직 그대로 유지 — 이 부분은 법정 계산이라 자유도가 없고 v1 설계가 맞다.

**3단계·4단계 fallback (데이터 미확보 상태에서도 막히지 않도록 지금 확정)**

| 단계 | 이상적 데이터 | 지금 쓸 fallback | ponytail 원칙 |
| --- | --- | --- | --- |
| 3 (영업지역 게이트) | 계약서상 영업지역 폴리곤/좌표 | 3-2에서 이미 쓰는 "최인접 5개 매장" Haversine 로직 재사용 → 반경 500m 내 동일 브랜드 매장 존재 시 자동 차단(등급 아님, 하드 스킵) | `ponytail: 반경 근사 게이트, 계약서 영업지역 데이터 확보되면 폴리곤 기반 정확 판정으로 교체` |
| 4 (본사 확장전략 우선순위) | HQ가 사전 등록한 타겟 상권 리스트 | 리스트가 비어있으면 이 가중치 항목을 0으로 두고 3-1 등급만으로 랭킹 (기능이 없어서 죽지 않고 자동 축소) | 별도 코멘트 불필요 — 입력 없으면 항목 생략은 정상 동작 |

이 fallback 덕분에 "계약서 영업지역 데이터가 시스템에 구조화돼 있는지"를 확인받기 전에도 설계·개발을 시작할 수 있다. 실제 데이터가 들어오면 3행의 로직만 교체하면 되고, 나머지 파이프라인(그리드 생성·랭킹·합의 절차)은 그대로 간다.

**동시성 규칙 (신규 추가)**: 동일 격자점이 서로 다른 상담 건에서 상위 후보로 겹칠 경우, 상담 접수일시가 빠른 건을 우선하고 후순위 건에는 "해당 입지는 타 상담 건과 중복, 대안 후보 제시" 안내를 자동 표기.

### 2-2. 재계약 가맹점주 트랙 (신규 설계)

**처리 로직**

```
1. 대상 매장의 브랜드/지역/비용구조/계약이력 피처를 조기경보 모델 pipeline.py에 입력
2. raw/calibrated 위험 스코어 + SHAP 상위 기여 요인 획득
3. 잔여 갱신요구 가능 기간(최초 계약일 + 10년 - 현재) 계산 → 법정 갱신요구권 대상 여부 라벨링
4. 위험요인 → 예방조치/재계약 조항 가이드 표(모델 산출물, docs/report.md 6절)에서
   해당 매장의 상위 SHAP 요인에 해당하는 항목만 필터링해 개인화
5. 상담자료 렌더링: [위험 스코어 요약] + [갱신요구권 대상 여부 고지] + [요인별 권고 조치·조항(권고안 명시)]
```

**출력**: 재계약 상담자료 — 법정 서면 아님, 표지에 "본 자료는 상담 참고용 권고안이며 법정 갱신거절 사유에 해당하지 않는 한 계약갱신요구권이 우선함"을 고정 문구로 표기.

**예외 처리**
| 상황 | 처리 |
| --- | --- |
| 갱신요구권 소멸(10년 초과) | 권고안에 "갱신 여부는 본사 재량" 문구로 전환 |
| 조기경보 모델 스코어 신뢰도 낮은 업종(예: 서비스업, Spearman 0.02 구간) | 스코어 대신 "정량 예측 신뢰도 낮음 — 정성 상담 권장" 경고 표기 |
| 법정 갱신거절 사유(가맹금 미납 등) 해당 | 별도 트랙(법무 검토)으로 라우팅, 이 기능 대상 아님 |

## 3. 남은 도메인 확인 필요 사항

fallback을 확정했기 때문에 아래 항목들은 더 이상 개발 착수를 막는 블로커가 아니다. 다만 fallback 정확도의 한계를 결정하는 정보라 실제 운영 전에는 사용자 확인이 필요:

- 본사가 실제로 "희망 상권 지도"를 사전에 보유·관리하는지 — 없으면 위 4단계는 3-1 등급만으로 랭킹(자동 축소), 있으면 그대로 가중치 반영. **동작에 영향 없음, 정확도만 좌우.**
- 기존 가맹점 계약서의 "영업지역" 조항이 좌표/반경 단위로 구조화돼 있는지 — 있으면 반경 근사(fallback)를 폴리곤 기반 정확 판정으로 교체. **없어도 반경 근사로 지금 개발 가능.**
- 재계약 시점 계약조건 변경 협상이 브랜드마다 얼마나 표준화돼 있는지 — 조기경보 모델의 5개 카테고리 가이드(업종구조/초기비용/업종분류/브랜드업력/계약기간구조)는 브랜드 무관 일반론이라 우선 그대로 사용 가능, 브랜드별 세분화는 필요성이 확인된 뒤 추가.

**지금 당장 필요한 것**: 위 세 가지 확인이 아니라, 2-1 3단계 fallback이 참조하는 "매장 좌표·전용면적·영업개시일" 필드(v1 6절에서 이미 지적된 신규 필드)가 매장 마스터 DB에 실제로 채워져 있는지 — 이게 없으면 fallback조차 못 돌린다. 이 필드 확보 여부가 유일한 실질 착수 조건.

## 4. 매장 마스터 DB 필드 확인 (2026-07-31)

이 저장소가 접근 가능한 공공데이터([[1. Projects/폐점 재계약 리스크 조기경보 모델]]이 쓰는 sbiz 상가업소 데이터·FTC 정보공개서)를 직접 열어 확인한 결과:

| 필드 | 공공데이터에 개별 매장 단위로 존재하는가 |
| --- | --- |
| 좌표(위도/경도) | 있음 (sbiz 상가업소 데이터 `경도`/`위도` 컬럼) — 주소만 있어도 지오코딩으로 즉시 파생 가능 |
| 전용면적 | 없음 — FTC 공개데이터는 브랜드 평균값(`avg_sales_per_area`)만 제공, 개별 점포 면적은 가맹계약서 원본에만 존재 |
| 영업개시일 | 없음 — FTC 공개데이터는 브랜드 단위 가맹사업개시일(`jng_biz_strt_date`)만 제공, 개별 매장 실제 개점일은 계약서/현장 데이터에만 존재 |

→ **전용면적·영업개시일은 어떤 공공데이터로도 대체 불가능.** 본사 내부 매장관리 시스템에 이 두 필드가 실제로 있는지가 이 기능의 진짜 전제조건이며, 이는 이 저장소 밖의 정보라 사용자 확인이 필요하다.

**중요한 구분**: v1의 3-2 입력표를 다시 보면 "후보 점포 전용면적"은 원래부터 **상담 시 담당자가 직접 입력**하는 필드다 — 매번 새로 입력하므로 DB에 미리 있을 필요가 없다. 진짜 필요한 건 **비교 대상인 기존 5개 매장**(과거 데이터)의 전용면적·영업개시일이며, 이건 신규 컬럼 추가(하루 작업)가 아니라 계약서 원본에서 과거 값을 역으로 채우는 **backfill**이 어려운 부분이다.

## 5. 개발 전략 — 가상 시나리오로 개발, 실전은 실데이터로 스왑

필드 유무 확인·backfill을 기다리지 않고 지금 개발을 시작하기 위한 방식:

1. `store_lat`, `store_lon`, `store_area_sqm`, `store_open_date` 4개 필드로 매장 마스터 스키마를 지금 확정
2. 매장 조회 인터페이스를 함수 하나(`get_nearby_stores(brand, lat, lon, n=5) -> list[dict]`)로 고정 — 3-1~3-4 로직은 전부 이 함수의 반환값만 사용하고 데이터 출처는 모름
3. 개발·테스트 단계: 이 함수를 실제 분포와 비슷하게 만든 가상 매장 10~20개(면적 20~150㎡, 매출 정규분포, 좌표는 실제 상권 좌표에 지터 추가)로 채운 mock 구현으로 대체
4. 실전 전환: 같은 함수 시그니처로 내부 DB 커넥터 구현체 하나만 교체 — 3-1~3-4 로직은 한 줄도 안 바뀜

`ponytail: mock 매장 마스터, 실제 매장 마스터 DB 연동 확정되면 get_nearby_stores 구현체만 교체`

**실행 검증 완료 (2026-07-31)**: 위 전략대로 mock 매장 12개 + 3-2 로직(6개월 미만 제외 → 최인접 5개 → 최댓값/최솟값 제외 3개 → 최저/최고 산정 → 1.7배 검증)을 실제로 구현·실행해 정상 동작 확인. 참고 구현:

```python
import math, random
from datetime import date, timedelta
random.seed(7)

def haversine_m(lat1, lon1, lat2, lon2):
    r = 6371000
    p1, p2 = math.radians(lat1), math.radians(lat2)
    dp, dl = math.radians(lat2 - lat1), math.radians(lon2 - lon1)
    a = math.sin(dp/2)**2 + math.cos(p1)*math.cos(p2)*math.sin(dl/2)**2
    return 2 * r * math.asin(math.sqrt(a))

def _mock_store_master(brand, center_lat, center_lon, n=12):
    today = date(2026, 7, 31)
    return [{
        "store_id": f"{brand}-{i:03d}", "brand": brand,
        "lat": center_lat + random.uniform(-0.02, 0.02),
        "lon": center_lon + random.uniform(-0.02, 0.02),
        "area_sqm": round(random.uniform(20, 120), 1),
        "open_date": today - timedelta(days=random.randint(60, 365*5)),
        "last_year_sales": round(random.uniform(1.5e8, 6e8)),
    } for i in range(n)]

def get_nearby_stores(brand, lat, lon, n=5):
    """실전 전환 지점: 이 함수 내부만 실제 매장 마스터 DB 쿼리로 교체."""
    ref_date = date(2026, 7, 31)
    eligible = [s for s in _mock_store_master(brand, lat, lon)
                if (ref_date - s["open_date"]).days >= 183]
    for s in eligible:
        s["dist_m"] = haversine_m(lat, lon, s["lat"], s["lon"])
    return sorted(eligible, key=lambda s: s["dist_m"])[:n]

def calc_expected_sales(brand, lat, lon, candidate_area_sqm):
    nearby = get_nearby_stores(brand, lat, lon, n=5)
    if len(nearby) < 5:
        return {"status": "산정서 자동생성 불가 (반경 내 5개 미만)"}
    for s in nearby:
        s["sales_per_sqm"] = s["last_year_sales"] / s["area_sqm"]
    ranked = sorted(nearby, key=lambda s: s["sales_per_sqm"])
    used = ranked[1:-1]  # 최댓값 1개, 최솟값 1개 제외
    low = min(s["sales_per_sqm"] for s in used) * candidate_area_sqm
    high = max(s["sales_per_sqm"] for s in used) * candidate_area_sqm
    ratio = high / low
    return {
        "status": "재산정 필요 (1.7배 초과)" if ratio > 1.7 else "정상 산정",
        "used_stores": [s["store_id"] for s in used],
        "excluded_stores": [ranked[0]["store_id"], ranked[-1]["store_id"]],
        "expected_sales_low": round(low), "expected_sales_high": round(high),
        "ratio": round(ratio, 3),
    }

# 실행 결과 (본죽, 서울시청 좌표, 후보면적 45㎡):
# {'status': '정상 산정', 'used_stores': ['본죽-002', '본죽-000', '본죽-009'],
#  'excluded_stores': ['본죽-010', '본죽-008'],
#  'expected_sales_low': 273092363, 'expected_sales_high': 307709325, 'ratio': 1.127}
```
