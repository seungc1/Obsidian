# 폐점 리스크 모델 v2 — 데이터 처리 과정 및 사용 기법

[[1. Projects/폐점 재계약 리스크 조기경보 모델]]의 v2(서울·매장 단위·LightGBM) 모델이 원자료를 어떻게 처리해 예측까지 이어지는지, 그리고 각 단계에서 실제로 쓴 전문 기법이 무엇인지 정리한 문서. 발표·질의응답 대비용 — [[3. Resources/폐점 리스크 모델 - 발표 슬라이드·대본 아티팩트 (초안)]]의 03·05·09·10번 슬라이드 내용을 근거와 함께 상세히 풀어썼다. **v2 기준으로만 정리**(v1은 언급하지 않음).

---

## 데이터 처리 6단계

### 1단계 — 수집
서울 열린데이터광장 API 9종에서 상권·유동인구·추정매출·상권변화지표·소득소비·실측폐업율(**CLSBIZ_RT**)을 가져오고, 통계청 SGIS 1km 격자로 배후인구를, 카카오 지오코딩과 서울교통공사 지하철역 276개 좌표(1~8호선만)로 위치 정보를 보강한다. 매장 좌표는 소상공인시장진흥공단 sbiz 상가업소에서, 브랜드 계약조건·비용 같은 공통 정보는 공정거래위원회 정보공개서에서 가져와 매장 데이터에 붙인다.

> **예상 질문**: "왜 브랜드 자체 데이터를 요구하지 않나요?" → 전부 공공 데이터만으로 구성해서, 브랜드가 자체 데이터를 제공하지 않아도 바로 적용할 수 있도록 설계했기 때문.

### 2단계 — 매칭

> **한 줄 요약(발표용)**: `269배 과매칭 발견 → 216개 정확 매칭`

- **브랜드명 매칭**: Aho-Corasick 문자열 매칭으로 FTC 브랜드 정보를 sbiz 매장에 연결. 단순 substring 매칭이 과매칭을 일으켜(원할머니 269배 등) **김가네만 정확 매칭으로 재작업**(216개), 나머지 브랜드는 보류.
- **좌표 매칭**: BallTree로 반경 250m·500m 내 경쟁밀도, 최근접 지하철역 거리 계산(좌표 30m 이내 매칭 기준)
- **상권 배정**: 매장 좌표를 최근접 상권 중심좌표에 매핑(폴리곤 경계 없는 근사치)
- **업종 크로스워크**: FTC 업종중분류와 서울시 음식점 분류(10개)를 근사 매핑

> **예상 질문**: "매칭 오류는 왜 생겼나요?" → 상호명을 부분 문자열로 매칭하다 보니 브랜드명이 다른 상호명 안에 우연히 포함되는 경우까지 다 잡혔기 때문. 대형 브랜드 354개 중 71개(20%)가 원본 대비 5배 이상 과다매칭됐고, 지금은 파일럿 브랜드(김가네)만 정정을 마친 상태.

### 3단계 — 정제

> **한 줄 요약(발표용)**: `버그 1개 → 지표 4개 동시 개선`

sbiz 중복 등록 행 3.4%를 제거하고 잠복해 있던 인덱스 버그를 수정했는데, 이 작업 하나만으로 본죽&비빔밥 사례의 Spearman이 0.353→0.460, 매장 생존 모델의 AUC가 0.522→0.541로 동시에 개선됐다. LightGBM은 결측치와 범주형 변수를 자체적으로 처리하기 때문에 별도의 전처리가 필요 없다.

> **예상 질문**: "알고리즘보다 데이터 정제가 더 중요했나요?" → 이 사례가 정확히 그걸 보여준다. 알고리즘을 바꾸기 전에 데이터 품질부터 손봐야 한다는 근거로 쓸 수 있음.

### 4단계 — 타겟 라벨
처음에는 시군구×업종 단위의 매크로 프록시로 타겟을 근사했지만, 서울 실측값과 대조한 결과 상관관계가 사실상 없어(R²<0.01) 폐기했다. 대신 **CLSBIZ_RT(상권×업종×분기 단위 실측 폐업율)를 매장 단위 타겟으로 직접 사용**한다. 같은 브랜드의 매장이라도 위치한 상권이 다르면 타겟값 자체가 달라지기 때문에, 라벨을 만드는 단계에서부터 매장 간 차별화가 가능해진다.

> **예상 질문**: "왜 처음부터 실측값을 안 썼나요?" → 매장 단위 실측 폐업율 자체가 흔한 데이터가 아니라서, 처음엔 근사치(프록시)로 시작할 수밖에 없었고 서울에서 실측 API를 발견한 뒤 전환했다.

### 5단계 — 피처
최종 채택 피처: 상권 추정매출·상권변화지표·유동인구(총량·점심·저녁)·행정동 소비지출·지하철 접근성·배후인구·경쟁밀도·브랜드 공통정보·업종 피어 평균 해지율. 가맹본부 재무·법위반은 매핑률 2~3%로 낮아서, 리뷰 평점·리뷰수는 신호가 약해서, 국민연금 소득데이터는 해상도가 너무 거칠어서(순위상관 오히려 하락) 최종안에서 제외했다.

> **예상 질문**: "가장 중요한 피처는 뭔가요?" → 상권 추정매출(SHAP 기여도 0.854, 압도적 1위). "브랜드 정보는 안 쓰나요?" → 쓰지만 순위는 가장 하위 — 입지가 브랜드보다 중요하다는 게 핵심 발견.

### 6단계 — 파이프라인
`pipeline_seoul.py`가 주소와 업종만 입력받으면 지오코딩부터 피처 생성, 예측까지 한 번에 처리한다. `build_seoul_feature_row()` 함수를 별도로 분리해서, 위험도 예측과 SHAP 설명이 지오코딩·sbiz 조회를 중복으로 하지 않고 같은 피처 행 하나를 공유하도록 만들었다.

> **예상 질문**: "이 코드가 실제 서비스에 바로 연결되나요?" → 아니다. 로컬 개발/참조 구현이고, 실제 OhDomi 서비스 통합은 별도 저장소(OhDomiAI)의 패치 병합 경로를 따라야 하며 API 엔드포인트 불일치 이슈가 남아있다.

## 출처별 데이터 활용 상세

6단계 처리 과정에서 실제로 어떤 기관의 어떤 데이터를, 어떤 목적으로 가져다 썼는지 **출처 단위**로 정리. 전부 공공 데이터이며, 브랜드 자체 제공 데이터는 사용하지 않는다.

### 1. 공정거래위원회(FTC) — 가맹사업정보공개서
- **원본 데이터**: 브랜드별 계약조건(최초·갱신 계약기간), 초기비용 구조(가맹비·교육비·보증금·인테리어비·이행보증금 등), 업종 분류, 사업개시일, 가맹점 변동 현황(연도별 계약종료·계약해지 건수)
- **관련 문서 번호**: 정보공개서 1102(가맹비 등)·1104(교육비)·1105(설비비)·1106(보증금)·1109(가맹점 현황)·1112(변동 현황)
- **v2 활용처**:
  - 브랜드 공통 정보(계약기간·비용)를 **2단계 매칭**에서 Aho-Corasick으로 각 매장 행에 결합
  - 브랜드×연도 실측 해지율을 "**업종 피어 평균 해지율**" 피처로 가공(SHAP 순위는 하위지만 여전히 사용 중)
- **한계**: 브랜드 단위 집계 자료라, 개별 가맹점 원자료(가맹점목록현황)는 COUNT 집계만 노출돼 구조적으로 확보 불가능

### 2. 소상공인시장진흥공단 — sbiz 상가업소
- **원본 데이터**: 전국 상가업소 274만 건 — 좌표(위경도)·상호명·업종소분류·행정동코드
- **스냅샷 시점**: 202603 단일 시점(연도별 변화는 반영 못 함 — 한계로 남음)
- **v2 활용처**:
  - 매장 단위 원자료의 뼈대(좌표·상호명·업종) — **1단계 수집**
  - 브랜드명 매칭 대상(Aho-Corasick) — **2단계**
  - 경쟁밀도 계산 대상(BallTree, 반경 250m·500m) — **2단계**
  - 완전 중복 3.4% 제거 대상 — **3단계 정제**

### 3. 서울 열린데이터광장 — API 9종 중 6종
| API | 원본 데이터 | v2 활용처 |
|---|---|---|
| 상권(영역) | 상권 코드·등급·업종 구성 | 매장의 상권 배정 기준(2단계) |
| 유동인구 | 시간대별 통행량(총량·점심·저녁) | 피처 — 세분화해서 사용(5단계) |
| 추정매출 | 상권 평균 매출 근사치 | 피처 — **SHAP 1위(0.854)** |
| 상권변화지표 | 성장·쇠퇴 등급(LL/LH/HL/HH) | 피처 — SHAP 2위(0.591) |
| 소득소비 | 행정동 단위 소비지출액(총액·음식) | 피처 |
| **CLSBIZ_RT**(점포-상권) | 상권×업종×분기 **실측 폐업율** | **타겟 라벨**(4단계 — v2의 정답값 그 자체) |

### 4. 통계청 — SGIS
- **원본 데이터**: 1km 격자 단위 인구 통계
- **v2 활용처**: 매장 좌표가 속한 격자의 인구를 "배후인구" 피처로 사용(5단계)

### 5. 카카오 — 로컬 API
- **v2 활용처**: 학습 데이터 구축용이 아니라 **실사용 파이프라인**(`pipeline_seoul.py`)에서 신규 입력 주소를 좌표로 변환하는 지오코딩 — 운영 시 실시간 조회(6단계)

### 6. 서울교통공사 — 지하철역 좌표
- **원본 데이터**: 지하철역 276개 좌표(1~8호선만)
- **v2 활용처**: BallTree로 매장별 최근접 역까지 거리 계산 → "지하철 접근성" 피처(2·5단계)
- **한계**: 9호선·신분당선·공항철도·GTX 등 다른 운영기관 노선은 미포함 — 해당 노선 인근 매장은 거리가 과대추정될 수 있음

### 출처 → 피처 매핑 한눈에 보기
```
FTC              → 브랜드 공통정보, 업종 피어 평균 해지율
sbiz             → 좌표·업종(원자료), 경쟁밀도
서울 열린데이터광장 → 상권변화지표, 유동인구, 추정매출, 소비지출, [타겟] 실측폐업율
SGIS             → 배후인구
카카오            → (운영 시) 지오코딩
서울교통공사        → 지하철 접근성
```

## 사용한 전문 기법 (용어 정리)

### 매칭·전처리
| 기법                 | 설명                               |
| ------------------ | -------------------------------- |
| **Aho-Corasick**   | 다중 패턴 문자열을 한 번에 탐색하는 문자열 매칭 알고리즘 |
| **BallTree**       | 공간 인덱싱 기반 최근접 이웃 탐색 자료구조         |
| **Fuzzy Matching** | 좌표+정규화 상호명 기준 근사(퍼지) 매칭으로 중복 판별  |

### 모델링
| 기법 | 설명 |
|---|---|
| **GBDT** (Gradient Boosting Decision Tree) | 여러 개의 얕은 결정트리를 순차적으로 오차를 줄여가며 앙상블하는 방식 |
| **LightGBM** | GBDT 계열, **Leaf-wise 트리 성장**(다른 트리모델의 Level-wise 방식과 대비) 방식으로 속도·정확도 우위 |
| **L1·L2 정규화** (reg_alpha / reg_lambda) | 모델이 과적합되지 않도록 가중치 크기를 억제하는 규제 기법 |
| **범주형 변수 네이티브 처리** | 원-핫 인코딩 등 별도 전처리 없이 모델이 직접 범주형을 학습하는 방식 |

### 튜닝·검증
| 기법                            | 설명                                                            |
| ----------------------------- | ------------------------------------------------------------- |
| **Random Search**             | 그리드서치처럼 모든 조합을 다 시도하지 않고, 무작위로 뽑은 조합만 탐색해 효율을 높이는 하이퍼파라미터 탐색법 |
| **Seed Stability Check**      | 같은 모델을 20개의 서로 다른 난수 시드로 반복 학습해, 단일 시드 결과가 우연이 아닌지 확인하는 절차    |
| **Wilcoxon Signed-Rank Test** | 짝지어진 두 표본(같은 데이터, 다른 알고리즘) 간 차이를 검정하는 비모수 통계 기법               |
| **시간 기반 Holdout**             | 무작위 분할이 아니라 과거→미래 순서로 학습/검증을 나눠 미래 데이터 유출을 막는 분할법             |

### 평가·해석
| 기법 | 설명 |
|---|---|
| **Spearman 순위상관** (ρ) | 두 순위 목록이 얼마나 일치하는지 측정(-1~1, 1에 가까울수록 정확) |
| **RMSE** | 평균제곱근오차 — 예측값과 실제값의 오차 크기 |
| **AUC** | ROC 곡선 아래 면적 — 분류 성능 지표(매장 생존 모델에서 사용) |
| **SHAP** (SHapley Additive exPlanations) | 게임이론의 **Shapley Value**를 응용해, 각 피처가 예측 결과에 기여한 정도를 수치로 분해하는 해석 기법 |

## 발표자료 반영 현황

20장 구성 중 이 문서와 직접 대응하는 슬라이드:
- **03번** 분석 로드맵 — 전체 흐름 한 장 요약
- **05번** 데이터 처리 과정 — 6단계 상세(이 문서의 1~6단계와 동일)
- **09번** 전처리된 데이터가 결과로 이어지는 흐름 — 모델 선정이 아니라 완성된 모델의 운영 흐름(전처리→예측→SHAP→백분위→매트릭스→조항매핑)
- **10번** 결과는 어디에 쓰이는가 — 역할별 활용표 + 6단계 운영 루프
