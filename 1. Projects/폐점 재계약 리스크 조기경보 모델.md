## 핵심 설계 요약
- 타겟: 폐업/철수 OR 재계약 실패를 하나의 "사업 중단" 리스크 스코어로 통합
- 라벨(2026-07-22 방향 전환): Cell(지역) 단위 매크로 프록시(A/B/C 가중합)는 서울 실측 검증 결과 예측력이 없음을 확인(v1/v2 모두 R²<0.01) → **FTC 가맹점 변동 현황(브랜드x연도 실측: 계약종료+계약해지)을 타겟으로 직접 사용**하는 방식으로 전환. Cell 단위 지표(A 순증감, KOSIS 소멸률)는 라벨이 아니라 브랜드가 속한 지역의 피처로 재활용 예정
- 모델: LightGBM 메인 트랙 계획했으나 이 환경의 애플리케이션 제어 정책이 네이티브 DLL을 차단해 scikit-learn `HistGradientBoostingRegressor`로 대체(2026-07-23). 베이스라인 Spearman 0.037 → 시계열 피처 0.084 → 표본크기 가중+정규화 0.161 → **경쟁밀도(반경 250m/500m) 피처 추가 후 최종 RMSE 0.2354(베이스라인 0.2386 이김)/Spearman 0.1653**(2026-07-23, 현재 최종 성능). 브랜드 개별 이력(시계열/등록취소이력/본부재무)은 커버리지를 100%까지 올려도 SHAP 기여도 0으로 확인돼 전부 기각 — 유효했던 신호는 업종 피어평균, 정적 비용/업종 피처, 경쟁밀도 세 축. 캘리브레이션은 보류, 여유 시 lifelines 생존분석 보조 트랙

### 2026-07-23 (계속) — 1순위 타겟 노이즈 진단 + 2순위 데이터 재처리, 개선의 실제 원인 특정
사용자 요청("지금 문제를 해결하기 위해서 필요한 자료나 과정 검토, 우선순위 나열")에 따라 5단계 우선순위를 세우고 상위 2개를 실행:

**1순위 — 타겟 노이즈 진단** (`src/models/diagnose_target_noise.py` 신설): 브랜드의 74%가 가맹점 10개 미만이라 타겟(해지율) 분산 대부분이 소표본 노이즈일 가능성을 확인. `sample_weight=sqrt(연초가맹점수)` 가중회귀 + 가맹점 10개 이상 서브셋 평가를 조합한 결과 Spearman이 0.084→0.097(가중)→0.122(서브셋)→0.158(가중+서브셋)로 일관되게 개선. 단, RMSE는 어떤 케이스에서도 평균-예측 베이스라인을 못 이겨 **노이즈가 실재하지만 단독 원인은 아님**을 확인 — 표본크기 가중을 기본값으로 채택.

**2순위 — 미활용 데이터 재처리**: (1) 1105(지역별 매출) 파싱 버그 발견·수정 — 기존 코드가 지역별 값을 전국값으로 오인해 흡수하던 구조적 오류였음, 수정해도 커버리지는 여전히 낮아(~1%) 모델에는 미포함. (2) 1111(등록취소 사유) 이력을 1년 지연시켜 피처화(커버리지 100%). (3) §8에서 커버리지 부족(15~40%)으로 SHAP 0이었던 시계열 피처 3종에 연도별 평균 imputation 적용(커버리지 99.9%로 상승).

**재검증 결과(표본크기 가중 반영)**: RMSE 0.2425(베이스라인 0.2386과 거의 근접), Spearman **0.156**. 하지만 SHAP 확인 결과 **이 개선은 전부 1순위(표본크기 가중)에서 온 것**이고, 2순위에서 추가/보강한 신규 피처(1111 취소이력 2종 + imputed 시계열 3종, 커버리지 100%/99.9%임에도) 전부 SHAP 기여도 정확히 0. §8의 "커버리지 부족 때문에 안 쓰인다"는 가설은 **반증**됨 — 브랜드 개별 이력과 이듬해 해지율 사이엔 애초에 실질적 상관관계가 없다는 뜻. 남은 유효 신호는 업종x연도 피어 평균과 브랜드 정적 속성(비용구조/업종/업력) 두 종류뿐으로 좁혀짐. 자세한 내용: `docs/design.md`의 "9. 1순위 진단 + 2순위 피처 보강"

### 2026-07-23 (계속) — 3순위: 피어평균 과의존 완화 시도 → 애초 전제가 뒤집힘
`induty_peer_avg_discontinuation_rate`가 SHAP 1위를 독점하는 현상을 정규화(`l2_regularization`/`min_samples_leaf` 그리드서치)로 완화할 수 있는지 확인(`src/models/tune_regularization.py`). **결과**: 정규화 강도를 바꿔도 이 피처의 SHAP 지배력(1위/2위 비율 약 2.8~2.9배)은 거의 그대로였고, 오히려 이 피처를 완전히 제거하는 참고 실험에서 Spearman이 0.156→0.105로 반토막남 — **"과의존은 해롭다"는 애초 전제가 틀렸음을 확인**. 이 피처는 억제 대상이 아니라 지금까지 확보한 피처 중 거의 유일하게 신뢰할 수 있는 신호로 재평가. 다만 `l2_regularization=10`은 RMSE(0.2425→0.2415)와 Spearman(0.156→0.161) 둘 다 손실 없이 개선하는 유일한 지점이라 기본값으로 채택. **결론**: 모델 구조를 만지는 접근의 개선 여지는 대부분 소진됨 — 다음은 신규 데이터 확보(브랜드↔가맹본부 매핑, 경쟁밀도) 또는 지금 수준에서 리포트/가이드 표 작성으로 전환 판단 필요. 자세한 내용: `docs/design.md`의 "10. 3순위"

### 2026-07-23 (계속) — 4순위: 브랜드↔가맹본부 매핑 시도, 매핑은 성공했으나 신호 없음
1106(재무)/1109(법위반)을 연결하려면 브랜드↔가맹본부 매핑이 필요했는데, **FTC 12개 파일 전체(88만+건)를 확인한 결과 브랜드명과 본부명이 동시에 채워진 레코드가 0건** — 정식 매핑 키 자체가 데이터에 노출돼 있지 않음을 확인. 대안으로 "본부명==브랜드명 정확 일치"(1개 브랜드=1개 회사인 소형 프랜차이즈에서 흔함) 방식으로 매핑해 연결 — 브랜드 3,443개 중 351개(재무, 10.2%)/2개(법위반, 0.06%) 매핑 성공. 영업이익/총자산/당기순이익/총부채/총매출/자본총계/부채자본비율(1106) + 시정조치수/민사소송실패수/과징금조정건수(1109) 10개 피처 추가 후 재학습. **결과**: RMSE·MAE·Spearman이 소수점까지 완전히 동일(모델이 새 피처를 전혀 안 씀), SHAP도 10개 전부 기여도 0 — 타겟 매칭 기준 실제 커버리지가 2~3%(재무)/0.08%(법위반)로 너무 낮았던 게 원인. §8/§9에서 반복된 "낮은 커버리지 → SHAP 0" 패턴이 네 번째로 재현됨. 매핑 방법(정확 일치만 지원, 다브랜드 회사 누락) 자체의 한계이지 "본부 재무건전성은 무관하다"는 증거는 아님 — 더 밀려면 매핑 정교화가 선행돼야 함. 4순위도 소진, §10의 리포트 전환 결론 유지. 자세한 내용: `docs/design.md`의 "11. 4순위"

### 2026-07-23 (계속) — 경쟁밀도 피처: 처음으로 RMSE가 베이스라인을 이김, 순위상관은 악화
1순위(경쟁밀도)를 재개. sbiz 상가업소(274만 건, 202603 단일 시점)에는 브랜드명이 없어 `상호명` 문자열에 브랜드명이 부분일치하는지 Aho-Corasick 다중패턴 매칭(`pyahocorasick` 신규 설치)으로 검색 — 타겟 브랜드 3,443개 중 **2,807개(85%)가 최소 1개 이상 매칭**(총 90,218개 점포). 매칭된 점포마다 같은 업종소분류 내 반경 250m/500m 경쟁 점포 수를 BallTree로 계산해 브랜드 단위로 평균(`src/features/sbiz_competition.py`). **커버리지 82.6%(3,263/3,951)** — 지금까지 추가한 신규 피처 중 최고. **결과**: RMSE **0.2344 — 이 프로젝트 전체에서 처음으로 평균값 예측 베이스라인(0.2386)을 이김**(1.8% 개선). 하지만 Spearman은 0.161→0.132로 오히려 나빠짐. ### 2026-07-23 (계속) — 매칭점포수 재검증 → 제거하니 세 지표 모두 최고치 갱신

### 2026-07-23 (계속) — DoD 잔여 3개 항목 완주: decile/subgroup 검증 → 캘리브레이션 → pipeline.py
사용자 요청("모델을 다 만든 거야?" → "끝까지 만들어야지 차례대로 진행해줘")에 따라 DoD에 남아있던 마지막 세 항목을 순서대로 완료.

1. **decile/subgroup 검증**(`src/models/evaluate.py`): valid를 예측 위험도 10분위로 나누자 실측 해지율이 완벽히 단조감소(1분위 0.251 → 10분위 0.091, 상하위 10% 간 2.75배 차이) — Spearman만 보면 약해 보였지만 극단 그룹 분리력은 실용적으로 쓸만함. 다만 **업종별로 쪼개보니 서비스 업종은 Spearman 0.02로 순위분별력이 거의 사라짐**(전체 평균 0.165가 이 편차를 가리고 있었음), 대형 브랜드(≥10점)는 0.227로 뚜렷이 더 좋음 — 종합 지표만 보고 "이 모델이 어디서나 똑같이 작동한다"고 오해하면 안 됨을 확인.

3. **`pipeline.py`**: 원래 스텁은 폐기된 Cell 2단계 구조(주소→좌표) 전제였던 걸 브랜드 피처 dict 입력 방식으로 전면 재작성. `python -m src.pipeline --input-json <파일>`로 raw/calibrated 스코어 출력 확인(`docs/pipeline_input_example.json`). 구현 중 범주형 컬럼 predict-time 카테고리 불일치로 인한 `TypeError`를 발견·수정(학습 데이터 전체의 카테고리 목록을 명시 지정하는 방식으로 해결).

### 2026-07-28 (계속) — v1 알고리즘 재검토: HistGBR → RandomForest 정식 교체
사용자 요청("다른 알고리즘은 예측률이 더 좋은지 확인해봐")으로 시작. `compare_algorithms.py` 신설해 8개 알고리즘(HistGBR·LightGBM·XGBoost·CatBoost·RandomForest·전통GradientBoosting·ExtraTrees·Ridge) 동일 조건 비교 → HistGBR이 1위(RMSE 0.2333/Spearman 0.1694). XGBoost·LightGBM은 예전(2026-07-23) WDAC로 막혔던 게 이번엔 정상 설치·작동 확인(정책 변화 또는 재설치로 해소 추정). 과정에서 버그 2건 발견·수정: ①2025년에만 등장하는 신규 업종(예: "약국")이 valid 카테고리를 독립적으로 잡아 XGBoost가 한글 에러메시지 인코딩(cp949→utf-8)으로 크래시 — train 카테고리로 강제 정렬해 해결. ②CatBoost cat_features가 category dtype의 `.astype(str)` 후에도 결측을 실제 NaN으로 남기는 pandas 버전 이슈 — object 경유 후 명시 대체로 해결.

`tune_algorithms.py`(알고리즘별 20회 랜덤서치) 결과 RandomForest가 튜닝 후 Spearman 0.175로 HistGBR을 앞서는 것 발견 — 단일 시드라 우연 가능성 의심, `seed_stability_check.py`로 20개 시드 반복 검증. **결과: RandomForest가 18/20 시드에서 승리, Wilcoxon 부호순위검정 p=0.0003(유의), RMSE·Spearman 평균 모두 우위 + 표준편차도 더 작음(더 안정적).** 기존 "HistGBR 현재 모델 성능"으로 인용해온 수치(seed=42, Spearman 0.169)는 이 모델 자체의 20개 시드 중 최상위권에 가까운 값(평균은 0.1195)이었음이 드러남 — 즉 그동안 다소 운 좋은 시드로 모델을 평가해온 셈.

**정식 교체 실행**: `train.py`의 `train_risk_model()`을 RandomForestRegressor(n_estimators=200/min_samples_leaf=5/max_features=1.0/max_depth=4, 랜덤서치 최적값)로 교체. RandomForest는 결측·범주형을 네이티브로 못 받아 `sklearn.pipeline.Pipeline`(`ColumnTransformer`: 수치형 SimpleImputer+범주형 OneHotEncoder `handle_unknown="ignore"`)으로 감싸, `model.predict(원본_df)` 호출부(`evaluate.py`/`calibration.py`/`pipeline.py`)는 전부 무수정으로 호환 유지. `compute_shap_summary()`는 SHAP PermutationExplainer의 tabular masker가 숫자+문자열 혼합 배열을 못 다뤄(`TypeError`) HistGBR 때와 동일한 카테고리→정수코드 인코딩 wrapper를 그대로 유지해야 함을 재확인. 모델 파일명 `baseline_hgbr_v1.joblib`→`baseline_rf_v1.joblib`로 변경.

**재검증 완료(전부 정상)**: 학습(RMSE 0.2355/Spearman 0.1750) → SHAP(1위 여전히 induty_peer_avg_discontinuation_rate, 스토리 불변) → decile(단조감소는 아니나 고위험군 lift 유지) → subgroup(서비스 업종 Spearman -0.023로 기존 약점 재확인) → 캘리브레이션(적용됐으나 홀드아웃 MAE 0.1740→0.1753로 미세 악화, 정직하게 기록) → 추론 파이프라인(`docs/pipeline_input_example.json`으로 raw/calibrated 스코어 정상 출력) 전부 확인. v2(`train_seoul_closure.py`)는 별도 파일에서 독립적으로 HistGBR을 쓰고 있어 이번 교체 범위 밖 — 그대로 유지.

영업방침 불수락/중요 영업방침 위반/가맹점주의 중대한 일신상 사유/천재지변) 없이는 위험도가

바로 위에서 발견한 결함을 그 자리에서 수정. **근본 원인**은 `clause_recommendation.py`의
`recommend_clauses()`가 v2는 실패를 흡수해 `v2_error`로 남기면서 v1은 예외를 그대로
전파시켰던 비대칭 설계 — 호출부(`renewal_packet.py`/`prospect_packet.py`)가 그 예외를

없다"는 뜻의 문구로 뭉뚱그려 보여주고 있었음. 두 문서 생성기 모두 같은 `_clause_section()`
헬퍼를 쓰므로 그 한 곳만 고치면 양쪽 다 해결되는 구조(재계약 쪽에서 먼저 만든 원칙 재확인).

**수정**: (1) `clause_recommendation.recommend_clauses()` — v1도 v2와 동일하게 try/except로

`_error` 존재 여부를 따로 안 챙겨도 되게 함). (2) `renewal_packet._clause_section()`/
`prospect_packet._clause_section()`에 `error` 인자 추가 — 있으면 내부용엔 "⚠️ 계산

기술적 오류 문구 없이 "지금 계산하지 못했습니다 — 문의하세요"로 완곡하게 표시. (3) v2
섹션 노출 조건도 `clauses["v2"] is not None`(실패해도 결과가 None이라 값을 구분 못 함)에서
`v2_attempted = bool(address and sbiz_category)` 기준으로 변경 — "애초에 시도 안 함"(주소
미제공, 정상)과 "시도했지만 실패"를 구분.

**검증**: numba DLL 차단 상태에서 `generate_prospect_packet()`을 mock 없이 실제로 호출해
내부용 문서에 "위험요인 근거 계산 실패(기술적 오류): ImportError: DLL load failed..." 문구가
뜨는 것을 확인(수정 전엔 "등록된 요인 없음"으로 잘못 표시됐던 자리). 두 파일 모두 새 테스트
(`test_clause_computation_failure_distinct_from_no_factors`) 추가해 "계산 실패" 문구가

### 2026-08-04 (계속) — 후보 브랜드/입지 수동+자동 지원, pytest 설치
지난 "다음 진행사항" 목록 중 "prospect_packet용 실제 후보 데이터 소스 미정"(브랜드 목록,

**pytest 설치**: `pip install pytest` — 10개 테스트 중 9개 통과, `test_pipeline.py`의

**후보 입지 자동화**: `suggest_candidate_location(brand_nm)` 신설 — 서울 sbiz 데이터에서
브랜드명이 포함된 매장을 찾아(`상호명.str.contains`) v2가 지원하는 6개 업종
(`SBIZ_TO_SEOUL_INDUTY`)으로 필터링한 뒤, 가장 많이 몰린 행정동(주력 상권으로 근사)의 대표
매장 주소+업종중분류를 반환. 매칭 실패(브랜드 없음/6개 업종 밖)면 `None` — 근거 없는 v2
계산을 만들지 않고 조용히 v1만 진행("확실하지 않으면 사람이 판단" 원칙 재적용). `apply_auto_location()`이 수동 입력(`address`+`sbiz_category` 기존값)을 항상 우선하고, 없을 때만
자동 추천을 시도. CLI `--auto-location` 플래그로 노출, 문서에는 "⚠️ 후보 입지 자동 추천
(참고용, 실제 부지 아님)" 안내가 항상 동반돼 예비창업자가 실제 정한 부지로 착각하지 않게 함.

**실행 중 발견해 그 자리에서 고친 결함 2건**:
1. `상호명.str.contains(brand_nm, ...)`가 `regex=False` 없이 호출돼, "티스테이지(TEE STAGE)"
   처럼 정규식 특수문자(괄호 등)가 든 실제 브랜드명에서 매치 그룹 경고와 함께 잘못된 결과를
   낼 수 있었음(`--all-brands`로 실제 브랜드명 5건을 돌려보다 발견) — `regex=False` 추가.
2. **더 심각한 결함**: `pipeline.py`의 `_fill_competition_density()`가 `sbiz_category`를
   상권업종소분류명(v1 세분류) 기준으로만 조회하는데, `suggest_candidate_location()`이
   채우는 값은 상권업종중분류명(v2 형식, 예: "한식") — 두 파이프라인이 같은 필드명을 다른
   세분화 수준으로 쓰고 있었음. 이 상태로 v1을 부르면 `query_live_competition_density()`가
   `ValueError`를 던지고 전체 `combine_score()`가 그대로 죽음(단건 실행 시 전체 크래시,
   배치 실행 시엔 해당 건만 "실패" 처리). 자동 추천 없이 사람이 직접 v2 형식 `sbiz_category`
   만 넣고 경쟁밀도는 안 준 경우도 원래부터 걸리는 구조적 결함이었음(이번에 처음 발견).
   `_fill_competition_density()`에 폴백 추가: 주어진 `sbiz_category`가 소분류명 목록에 없으면

**EC2 배포 영향 점검**: "우리 EC2에서도 돌리고 있는데 이번 변경이 거기에 영향 있는지"
질문에 3개 저장소(`closure-risk-model`/`OhDomiSpring`/`OhDomiReact`) 전체를 grep했지만
EC2/AWS 관련 설정·Dockerfile·CI/CD가 전혀 없어(Spring의 DB URL도 환경변수+로컬 기본값)
저장소만으로는 실제 배포 방식을 알 수 없었음 — 사용자에게 직접 확인한 결과:
- EC2는 **수동 배포**(SSH 접속 → git clone → `models`/`data` zip 번들 수동 병합 → `.env`
  수동 생성 → conda 환경에서 `uvicorn ... --host 0.0.0.0 --port 8001` 직접 실행 → nohup으로
  상시화)이며, **main/master 브랜치 기준**으로 돈다.
- 원래 배포 가이드는 별도 저장소 `OhDomiAI`(`service/main.py`가 `CLOSURE_RISK_MODEL_PATH`로
  이 레포를 라이브러리처럼 import)를 실행하는 구조였는데, 위에서 발견한 팀원의 `/risk/predict`
  커밋이 **이 레포 자신의 `src/api.py`에 직접** 추가돼 있어 — 실제로 지금 EC2가 `OhDomiAI`를
  통해 도는지, 아니면 이 레포의 `src.api:app`을 직접 띄우는 쪽으로 이미 바뀌었는지는 이
  세션에서 확인 불가(팀원 확인 필요, `OhDomiAI` 저장소 로컬에 없음).
- 이번 세션 변경분은 `/risk/predict`가 쓰는 `combine_score()`/`recommend_clauses()`/
  `score_store()`/`score_seoul_store()` **시그니처를 하나도 안 바꿈** — 전부 `@lru_cache`
  성능 개선(§2026-08-07)이나 새 함수 추가, 그리고 위에서 확인한 분류 문구 1건뿐. **코드
  자체는 EC2에 안전하게 배포 가능**.
- `web/` 대시보드가 쓰는 신규 캐시 파일(`kimgane_risk_rankings.json`의 `v2_top_factor`,
  `kimgane_district_stat_avg.json`)은 전부 `.gitignore` 대상(`data/interim/**`)이라 git
  push로는 전달 안 됨 — 애초에 `/risk/predict` 경로가 안 쓰는 파일이라 EC2의 기존 모델/
  데이터 번들(`models/`, `data/raw`, `data/interim`의 학습용 CSV 6개)에도 영향 없음. 즉
  **이번 병합만으로는 EC2에 새로 옮겨야 할 데이터 파일이 없음**.
- 새로 추가된 `MOLIT_SERVICE_KEY` 환경변수(국토교통부 실거래가 API, `/district-trade-price`
  엔드포인트 전용)는 미설정 시 `RuntimeError`를 잡아 `{"available": false}`로 우아하게
  대체하도록 이미 만들어져 있어(`api.py:426-430`) — EC2 `.env`에 없어도 서버가 죽지 않음,
  다만 이 기능만 조용히 비활성 상태로 남음(우선순위 낮은 후속 조치로 기록).
- 팀원 커밋이 `requirements.txt`에 `Markdown>=3.5`를 추가함 — EC2가 다음에 코드를 pull할
  때 `pip install -r requirements.txt` 재실행 필요(모델 번들과 무관, 코드 배포 시 통상
  절차).

**결론**: 오늘 병합분은 EC2의 기존 `/risk/predict` 경로를 깨지 않음(시그니처 불변,
문자열 매칭 비충돌 확인, 테스트 통과). 다만 실제 EC2가 `OhDomiAI` 경유인지 이 레포
직접 실행인지가 이 세션에서 불명확하므로, 다음 배포 전 팀 확인 필요.

**후속 확인 — `OhDomiAI` 저장소를 직접 클론해 대조한 결과, 실제 배포 불일치 가능성 발견**:
`OhDomiAI`(`feature/closure-risk-score` 브랜치, `service/main.py`)를 읽기 전용으로 클론해
확인해보니, 이 서비스가 노출하는 엔드포인트는 `/health`·`/risk-score`·`/demo-stores*`
뿐이고 **`/risk/predict`가 없음** — 팀원(joon0017)이 만든 `/risk/predict`는 오직
closure-risk-model 자신의 `src/api.py`에만 존재한다. 그런데 `OhDomiSpring`의
`application.yaml` 기본값은 `RISK_MODEL_BASE_URL=http://127.0.0.1:8001`,
`RISK_MODEL_PREDICT_PATH=/risk/predict`이고, 원래 EC2 수동배포 가이드(§2026-08-08 위
문단)는 정확히 이 8001 포트에 `OhDomiAI`(`service.main:app`)를 띄우는 절차였다 — 가이드
그대로 배포됐다면 Spring이 호출하는 `/risk/predict`가 **404로 실패할 가능성이 높음**
(OhDomiAI엔 그 경로가 없으므로). EC2에 지금 실제로 뭐가 떠있는지 이 세션에서는 확인할
방법이 없어(SSH 접근 없음) 사용자에게 팀원 확인 질문 문구와 EC2 자가진단 커맨드
(`ps aux | grep uvicorn`, `curl .../health`, `curl -X POST .../risk/predict`로 404 vs
422 판별)를 전달함 — 결과 확인 후 이어서 조치 필요.
